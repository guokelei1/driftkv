## 当前 Design 与 Implementation

2026-10-15当前方案采用候选内容门控读取、两阶段教师校准，以及可合成码／单缓冲锚码接续。
一份原生K/V与共享12＋每头私有6的码持续维护；当前每头读取共享3＋私有3。
主行为任务与原反馈任务的质量和成本分别报告，原反馈仍未达到联合80%／20%目标。
机制与证据见[Query relay报告](results/query_relay_2026_10/report.md)。
工程优化独立放在[implementation_2026_10](scripts/implementation_2026_10/README.md)，
覆盖共享码准备、融合读取、分块原地转换与系统集成；[本轮实验索引](results/implementation_2026_10/README.md)记录实现等价及资源边界。

## 历史选定方法与保留证据

1. **紧凑读取校正**：一份原生K/V与rank8代码，共享Key/Value投影在一次历史扫描中校正读取。
2. **发布前校准**：局部读取对齐后，通过冻结推荐模型联合对齐最终分数；线上参数固定。
3. **持续状态管理**：首次读取编码，随原生行追加/淘汰；既有依赖标记限定逐行校正范围，重建或全层依赖清除后退出。

选定开发候选`fullitem8_local_kv32_joint16_support_lazy`在固定4096用户、51,731请求、
V2→V3→V4→V5连续回放中恢复84.8066%。固定30k真实服务事件账上的完整新增计算为18.4375%。
代码与因果标记占原生K/V的12.5651%。V5相对未门控控制回退，配对增益区间跨零；
该开发点不是独立确认，超过历史80%参考不代表最终成功。

Full主参照是每用户每发布首次请求重建一次，之后正常增量服务。
逐请求Fresh只保留历史诊断身份，不能用作当前完整成本的100%分母。

2026-10-13新增第4.4节部分刷新原型：保存旧码及独立编码版本，发布验证后只刷新
选定尾部与缺失/过旧条目。冻结strict策略在另一组全部3360位合格benchmark用户上
保留96.04%全量码收益（UID95%区间93.35%–97.47%），发布刷新编码节省9.41%，
完整新增FLOPs节省0.51%。整体尚未通过至少95%保留的区间判据；长历史用户更稳定，
纯新用户上全量方法也回退。该案例不替代既有开发候选，也不构成全方法盲确认。
原型、成本边界与正负结果见[本轮报告](results/partial_refresh_2026_10/report.md)。

2026-10-14第二轮测试后，固定归一化折叠与同物品仿射项复用达到更强的维护计算节省：
仅批内复用35.10%，静态4k物品表49.94%（按4worker独立准备收费），3360用户上
全量compact code收益保留约100%、区间下界超过90%。主要节省来自等价编码计算复用，
两个点仍全量生成行码；激进少刷行数、长度分组和旧码重要性方案未达到质量目标。
完整新增计算分别省8.87%/12.61%，原方法的新用户回归仍在。
详见[第二轮结果与边界](results/partial_refresh_2026_10/round2/report.md)。

## 有效入口

2026-10-14共享码结构探索已完成：共享12＋每head私有6在相同48个FP32码数下，
每head可使用18维；固定4096开发用户上恢复89.4308%，完整新增FLOPs18.6369%。

该原型是D1/D2的表示结构探索，D3及旧默认入口保持原样。
