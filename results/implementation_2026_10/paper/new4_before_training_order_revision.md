# 第四章 CacheTide 设计

本章介绍 CacheTide 如何在连续模型发布中复用历史 K/V 缓存，并支持后续行为追加。

## 4.1 设计概览

模型更新后，新模型仍要读取此前保存的用户历史。重新编码这些历史会重复计算，直接读取旧 K/V 又可能偏离新模型重建历史时的响应。CacheTide保留原生 K/V，并维护紧凑码。读取时，系统根据当前候选物品，利用紧凑码调整历史匹配分数和聚合内容，从而纠正新模型的历史读取。

每次发布前，系统选取少量用户，将实际保留的缓存与新模型重建的缓存配对，学习码的更新规则和读取参数。部署后，请求复用已经准备好的码，并由当前候选物品决定本次纠正。发生新行为时，当前模型同样读取这些历史，再生成并追加新的 K/V。这样，发布前学习的纠正既服务于当前推荐，也支持历史继续增长。

后续发布继续保留原生 K/V，更新码及其读取参数。CacheTide 将多次码更新合并，使用户即使缺席若干次发布，返回时也能直接准备最新码，无需逐版重放。

下文依次介绍请求中的读取纠正（第 4.2 节）、发布前的参数校准（第 4.3 节），以及连续发布下的码更新与状态维护（第 4.4 节）。

## 4.2 用紧凑码纠正历史读取

注意力读取包含两项工作：Key 决定当前 Query 如何匹配历史，Value 决定匹配之后取回什么内容。CacheTide 用紧凑码为这两项工作提供纠正信息。

*（配图说明：此处放置“紧凑码的生成与结构”示意图。左侧以同一用户某层的一条继承历史为例，将原生 K/V、对应历史物品的信息和已有码状态作为三路输入，送入参数跨用户共享的“码生成模块”，输出当前紧凑码。模块内标出两类历史特征提取分支：共享分支读取全部头的 K/V，私有分支各读取本头的 K/V，两者都使用对应历史物品的完整固定表示；这些特征再与已有码状态和该历史物品的当前表示共同用于生成当前码，具体更新规则留在第 4.4 节展开。右侧放大输出码，将其画成一份共享段和各头的私有段：六个头时，共享段 12 维、每个私有段 6 维，完整码共 48 维；一般宽度为 $12+6H$，其中 $H$ 为头数。再以两个头为例，用“固定选取坐标”展示它们如何从同一个共享段和各自的私有段取出读取码。共享段只画一份；每头最多可选 18 个坐标，实际读取可以更少，未选中的坐标仍保留并参与后续版本更新。）*

如图所示，紧凑码是与原生 K/V 对齐保存的低维辅助表示。它由跨用户共享的码生成模块准备：模块结合保留的 K/V、对应历史物品的信息和已有码状态，输出供当前模型使用的码。系统用新模型重建的历史学习码的生成规则和读取参数（第 4.3 节）；跨版本的更新与合并规则见第 4.4 节。

如图所示，码生成模块在提取历史特征时，共享分支联合读取同一条历史在所有头中的原生 K/V，私有分支只读取本头的 K/V；两者都结合该历史物品的完整固定表示。共享分支使各头能够利用跨头的历史线索，私有分支则保留本头的细节。由此，共享码集中保存供各头复用的信息，私有码为各头不同的读取纠正需求保留独立容量，在控制存储开销的同时保留头间差异。

**候选请求到来时。** 当一个候选进入评分流程时，当前模型需要从用户历史中取得与该候选有关的信息。CacheTide 将保留的 K/V 与紧凑码共同用于这次注意力读取：历史 Key 和码一起确定匹配分数，历史 Value 和码一起形成取回的内容，最终得到供模型继续评分的历史响应。

本次请求沿当前模型的原有路径生成 Query，保留时间、行为类型和历史上下文。同时，系统根据候选物品的当前表示计算两组门控系数，分别控制码如何参与匹配和内容聚合。读取历史时，Query 与原生 Key 的匹配构成基础分数，码提供候选相关的补充；得到的权重随后用于汇总原生 Value 和码，形成输出。因此，在复用相同历史 K/V 和码的情况下，匹配权重与读取内容仍能随候选变化。

**Key 侧：共同计算注意力分数。** 以下以一层中的一个头为例。当前 Query $q$ 与第 $i$ 条历史的原生 Key $k_i$ 给出基础分数 $q^\top k_i$。该头还从共享部分和自己的私有部分取出读取码 $z_i$，用它补充候选与这条历史的匹配。

为让 Query 与码匹配，投影 $P_K$ 将 $q$ 降到码的宽度，再由本次候选的 Key 门控 $g_K$ 调整各维，得到 $\tilde q=(P_Kq)\odot g_K$，其中 $\odot$ 表示逐维相乘。最终的历史匹配分数为

$$
s_i=
\underbrace{q^\top k_i}_{\text{原生匹配}}+
\underbrace{\tilde q^\top z_i}_{\text{码提供的纠正}}.
\tag{4-1}
$$

本次候选的 $g_K$ 由各条历史共用，但不同的 $z_i$ 会给出不同的分数补充。原生 Query $q$ 继续匹配原生 Key，$\tilde q$ 则匹配码。系统按当前模型的缩放、激活和可见性掩码，将合并后的分数转换为注意力权重 $\alpha_i$，用于接下来的内容聚合。

**Value 侧：共同形成读取内容。** 得到权重后，系统用同一组 $\alpha_i$ 分别汇总原生 Value $v_i$ 和读取码 $z_i$。Value 的加权和提供原有的历史内容，码的加权和则提供附加信息。当前候选的 Value 门控 $g_V$ 调整这些附加信息，再由投影 $P_V$ 将其从码的宽度映射回原生 Value 宽度，与原有内容相加：

$$
o=
\underbrace{\sum_i\alpha_i v_i}_{\text{原生内容}}+
\underbrace{P_V\!\left[g_V\odot\sum_i\alpha_i z_i\right]}_{\text{码提供的补充内容}}.
\tag{4-2}
$$

两个加权和使用的是 Key 侧共同确定的历史权重；$g_V$ 调整码带来的内容补充，不另行分配历史权重。所得 $o$ 是该头面向当前候选的历史响应，随后继续进入当前模型。

上述两组门控在各头内独立计算：对候选物品表示做 RMS 归一化后，分别经过 Key、Value 的线性变换和 $1+\tanh(\cdot)$，得到与读取码同宽的系数。

**联合读取的作用与开销。** 这一过程保留原生 K/V 的数值及基础匹配、聚合计算，并通过紧凑码引入候选相关的补充。两个投影及生成门控的参数在发布前校准，同一服务版本内固定。行为追加以本次行为物品沿用相同路径。

Query 投影和门控每次读取只计算一次，K/V 与码可以在同一次历史遍历中处理，码聚合后只需一次回投影，无需逐条历史执行请求相关的非线性编码。门控固定时，纠正可折成固定的有效 K/V；随候选变化时，一般无法预先合并，因此系统复用历史码，在本次读取中形成具体纠正。

## 4.3 在发布前学习纠正

每次发布前，CacheTide 训练三类参数：紧凑码的更新参数、Key/Value 读取投影和候选门控参数。推荐模型保持冻结，训练目标是让当前模型使用保留缓存时，得到接近重建历史的读取响应与最终评分。

训练数据来自少量用户在发布前已发生的历史。系统以上一服务版本实际留下的 K/V 和码作为固定输入，再用当前模型重建相同历史，得到教师缓存。两套缓存配合同一组已知候选构成训练样本，监督来自重建路径，无需未来请求标签。拟合、选参与独立质量验证分别使用不同用户。

**第一阶段：逐层对齐读取。** 这一阶段的目标是让每层从保留缓存中读取到接近教师的历史信息，为后续层的计算提供经过纠正的输入。上层 Query 依赖低层的读取结果，系统因而从低层向高层推进：每层用已校准低层路径产生的同一个 Query 读取两套缓存，将比较集中在当前层的历史响应上。训练最小化纠正后响应与教师响应的平方误差，比较前采用相同的长度归一化和固定头尺度。

**第二阶段：联合对齐评分。** 第一阶段关注各层的历史响应，尚未直接约束整条推荐路径的评分，也未覆盖在继承历史上继续追加行为的过程。第二阶段因此沿完整评分路径联合调整各层纠正参数，直接对齐同一候选在重建完整历史上的评分。训练使用两种方式：直接读取全部保留历史，对应推荐请求；留出已观察历史的短尾，先纠正读取前缀，再按时序编码尾部，模拟在继承状态上追加行为。模型权重仍冻结，评分梯度通过续写的 K/V 传回纠正参数，使监督覆盖读取对后续状态的影响。两种评分平方误差等权平均。

## 4.4 连续发布中的码更新与维护

第 4.3 节训练了单次发布中的读取纠正，连续发布还需要支持历史追加和用户跨版本返回。CacheTide 将紧凑码的构造分解为逐行保存的状态与版本相关的变换，跨发布保留前者，读取前再构造当前码。

行为追加会使同一窗口包含不同版本生成的 K/V，而这些行都需要使用面向当前模型的码。用户还可能在一次访问后缺席若干次发布。如果一直保存某个旧版本使用的码，系统就需要逐版更新它，或继续保留解释旧码所需的版本参数。为避免这种依赖，CacheTide 将逐行保存的状态与当前版本的变换分离。

为实现这种分离，我们将码更新设计为对旧码施加可逆线性变换，再加入固定历史特征和当前物品信息。多次这样的更新可以合并，使版本变化由变换参数和物品项承载，而每条历史保留一份固定的输入状态。我们将这份状态称为锚码 $a_i$，并据此构造当前码：先用本版参数变换锚码，再补充从原生 K/V 和物品信息计算的项。锚码与当前码同宽。记当前码为 $c_i^{(t)}$，从原生 K/V 与完整固定物品表示提取的历史特征为 $\eta_i$，物品 ID 为 $m_i$，则

$$
c_i^{(t)}=P_ta_i+Q_t\eta_i+D_t(m_i).
\tag{4-3}
$$

其中，$P_t$ 将保存的锚码变换到当前版本，$Q_t\eta_i$ 和 $D_t(m_i)$ 分别补充历史特征与物品信息。跨发布时，每行只保留锚码；历史特征可以从已有输入重算，版本变换参数统一保存，不逐行复制。锚码根据当前码、该行输入及版本参数反算得到，无需单独训练。这一分解改变的是码的保存和构造方式，码的维度保持不变。

读取历史前，系统先按行计算 $\eta_i$，再完成两次小矩阵乘法和一次物品项查表，将三项相加，得到供第 4.2 节使用的当前码。结果覆盖原码缓冲区，同版后续请求直接复用。不同版本生成的行使用自己的锚码和历史特征，因此可以由同一套当前参数构造；用户跨过多次发布后，也无需生成中间版本码。准备成本包含固定特征计算，随历史长度增长，而不随缺席发布数增长。

上述更新规则的参数由第 4.3 节校准。每次发布时，系统将本次学得的更新与已有变换合并，得到式（4-3）中供所有用户使用的本版参数。

系统为每个用户的码缓冲区记录保存形式，以及当前码对应的服务版本，以判断能否直接复用。若保存的是锚码，便用本版参数构造当前码；若已经是本版当前码，则直接读取。发布交接时，系统先结束旧版操作，用旧参数将全部旧当前码反算为锚码，完成后才能移除旧参数；已经保存锚码的用户无需转换。新追加行先保存零当前码，在下一次交接时同样转为锚码。由此，用户的码状态与发布参数可以分别维护，每个用户始终只需一份码缓冲区。

**服务与成本细节。** 缓冲区记录码的形式和版本，推荐与行为追加均先准备当前码，活跃用户可提前准备；交接期间新旧表并存。新行为读取当前历史后，追加当前模型生成的原生 K/V 和零当前码，其锚码一般不为零；FIFO 同步移除 K/V 和码，已知零码后缀可跳过码运算。窗口可混合不同版本的行，新行也可能继承读取误差，因此校准使用实际状态并加入短尾续写。每行只存一份定宽码；全局固定编码器、物品表、发布表及读取参数，以及准备计算、在线纠正、过渡双表和临时张量均需计入成本。物品项可共享准备，历史特征仍按用户行计算。合并要求存活原生行、物品 ID 空间、模型结构及条目语义稳定；代数等价不保证长期读取质量，块正交与实际求逆也无法消除长期偏移造成的有限精度抵消。
