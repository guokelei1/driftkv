# 三规模相邻版本 Reuse 评测

本目录专用于选定 Medium、Large、Max 各 V0→V1 至 V4→V5 的 15 条相邻边。
Parent/Current Full 使用现有封存分数；新 GPU 任务只计算 Current 读取上一版缓存的
Reuse 分数。每条边采用原 E14 请求集、1024 条发布前历史、发布后按时间追加与淘汰；
不跨版本复用，也不以 Reuse 与 Full 的差值方向作为中断条件。

代码在 [`scripts/unified_reuse_2026_09/`](../../scripts/unified_reuse_2026_09/)，
固定计划在 [`configs/unified_reuse_2026_09/adjacent_e14.json`](../../configs/unified_reuse_2026_09/adjacent_e14.json)。
`--prepare` 只核对现有 Full 原始分数封存、权重及请求身份，生成四卡请求分片；
`--probe` 仅在小样本上测数值、吞吐与显存。正式 `--run` 已于 2026-09-23
经用户授权启动，并于 2026-09-25 完成。

正式运行每条边同时使用 GPU 0–3，各卡处理不重叠的用户分片；15 条边串行。
每卡 PyTorch 显存分配上限为总量 70%，任务开始时要求至少 75% 空闲。
模型按预设 cohort batch 处理，遇到显存不足只缩小当前 batch 并重试，不跳过用户。
原始 Reuse 分数按 128 用户一片原子写入并记录哈希；中断后跳过已封存分片。
分片还绑定权重、请求、计划和执行源码哈希，避免续跑时混用不同实现。
每条边完成后与原 Full 请求逐一核对，读取原标签汇总 AUC、log loss 等指标。
`status.json` 在边完成后及运行期间约每两小时刷新，包含已完成结果和当前边进度。

## 2026-09-23 准备与资源探针

15 条边共 6,962,068 条已知目标请求（Medium 661,736；Large 1,780,940；
Max 4,519,392），均已与原 Full 请求 ID、UID 和时间戳逐一核对。
一条代表边 V4→V5 的四卡小样本均完成；与原逐用户 Reuse 评测器比较，
各卡最大 logit 差不超过 `9.54e-7`。Max 探针还验证了短历史用户的回退路径。
发现并修正了同时间戳事件在批量入口中可能按 raw item 顺序排列的问题；
新 Reuse 路径按既有逐用户缓存定义的 mapped item/behavior 顺序生成发布缓存。
