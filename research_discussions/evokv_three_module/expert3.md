我第一轮最核心的判断是：**EvoKV 不应该把自己定义成“用便宜方法把旧 KV 修得更像新 KV”，而应该定义成“寻找一种远小于完整 Current KV、但对 Current 推荐决策足够等价的版本适配状态”。** 这里也必须把计算节省的来源说准确：PRO 便宜，不是因为 candidate bank 共享——Exact recomputation 同样可以被候选共享；真正的节省来自于它没有把用户的完整长历史重新经过 Current 模型的所有层，也没有重新物化和写回完整 Current KV，而只在 reader 聚合边界计算一个紧凑的用户级适配量。Candidate bank 的共同消费只是说明这份 sidecar 具有较高的后续复用价值和明确的推荐语义，不是它相对 Exact-All 便宜的根本原因。

对于 One-Release，我认为最值得研究的问题是：**Parent→Current 的模型变化，在推荐 reader 看来，是否可以分解为“大部分仍可继承的历史状态”与“一小部分 Current-version user adaptation”**。如果这个结构成立，那么正确的迁移对象就既不是 token，也不是完整 KV，更不只是一个孤立的 correction tensor，而是一种功能状态：旧 persistent state 继续承担大规模历史记忆，Current sidecar 负责修正新 reader 对这段历史的解释，两者共同近似 Current Exact。它的推荐辨识度也应该建立在这里：不是简单证明某些 token 或 K/V 可以少算，而是证明模型版本失配在经过 HSTU 的历史聚合和 candidate compatibility 计算后，会集中表现为一个低维、用户上下文化、能够跨候选复用的功能偏差。这个判断必须通过跨 candidate panel、跨时间、novel candidate 和 rolling append 的泛化来证明；否则 reviewer 很容易认为 sidecar 只是在某个冻结评测集上拟合 logits。

当前 PRO 已经足以证明这种功能分解“可能存在”，但还没有证明现有表示就是最终正确边界。AUC 五条边全部提升，而 log-loss 只有三条边提升，我的第一反应不是立即增加更复杂的迁移结构，而是先判断剩余误差究竟是什么：它可能已经较好地恢复了候选间的相对几何关系，却没有稳定恢复 score 的尺度、偏置或概率校准。应当先把 residual 分成 edge-level bias/temperature、user-dependent calibration 和真正的 candidate-conditioned error。若一个很小的校准分量就能把 log-loss 补齐，说明 PRO 的主体结构可能已经接近正确；若校准后仍然存在明显版本边差异，才说明 reader correction 还缺少一种能够描述候选方向或历史子空间的结构。在 10%–20% Exact 预算下，我建议不要只报告“比 Reuse 好”，而要报告恢复了多少 Reuse→Exact 的 release gain。大致而言，恢复一半只能算路线成立；能够在 Medium、Large 和多条 release edge 上稳定恢复约 70% 以上，并且 AUC、log-loss、排序指标和高风险用户群都不出现系统性退化，才足以成为论文第一项核心贡献。与此同时，成本必须同时包括 FLOPs、旧状态读取、raw-history 读取和新状态写回，而不能只保留 9.1% 这个理论计算数字。

Continuous 的核心风险也不是简单地“每次有一点误差，所以误差线性相加”，而是**后续迁移开始消费前一次迁移产生的近似状态，而不是 Exact source state**。换言之，\(v_1\rightarrow v_2\) 的迁移器可能是在 Exact \(v_1\) 上设计的，但真实输入却是 \(v_0\rightarrow v_1\) 产生的近似状态，这会形成状态分布漂移，误差可能被后续 reader 放大。因此，这一部分最重要的一句话原则应该是：**每次迁移产生的状态必须同时对未来事件 append 和下一次版本迁移保持闭包，并且未消除的误差必须显式记账，不能隐藏在不断叠加的 sidecar 或 lineage 中。** 我认为最简单可信的机制不是规定“每隔几版重算”，而是每次都把状态规范化到同一种 Current-compatible canonical form，只保留一个当前版本的适配层，而不是无限堆叠 \(v_0\rightarrow v_1\)、\(v_1\rightarrow v_2\) 的 correction chain；同时维护一个能够被 sampled Exact 校准的 debt estimate。长期保证不应该是业务 AUC 每版单调增加，而应该是相对 Current Exact 的差距有界，例如满足类似 \(d_{t+1}\leq \alpha_t d_t+\epsilon_t\) 的关系：要么迁移本身具有一定收缩性，要么系统通过更强 repair 或稀疏 Exact rebase 把 debt 截断。Sampled Exact 应承担误差估计和分布外检测，真实行为反馈负责验证长期业务效用，而 Rebase 应当是少量高债务用户的安全阀，不应成为 Continuous 的主体算法。

对于 GPU Runtime，我目前的先验是：当逻辑计算已经降到 Exact-All 的约十分之一后，真正的瓶颈很可能从矩阵计算转向 persistent-state bandwidth、ragged workload 和隐藏的状态物化。最关键的问题不是怎样把更多用户简单塞进 batch，而是：**物理执行量能否真的只与迁移计划触碰的状态成比例，而不是因为 kernel 和数据布局限制，最终仍然扫描、展开或者写回整份用户 KV。** 如果计算 sidecar 仍需为每个用户完整读取所有层、所有 token 的 KV，那么 9.1% FLOPs 很可能无法转化成接近量级的 makespan 降低。真正具有论文价值的 Runtime 应围绕迁移特有的数据流，把旧状态读取、必要的 reader transformation、聚合和 sidecar generation 融合起来，避免中间 Current KV 的物化，并按照版本边、历史长度、实际访问的 token/layer 数和存储层级组织 batch。这里的共享结构是“海量用户执行同一条 Parent→Current transition”，而不是 candidate bank 共享。Runtime 是否能成为独立贡献，要看它能否相对一个已经做好 bucketing、异步 prefetch 和通用 GPU kernel 的强基线，进一步显著降低实际读取字节、GPU-hours 和全人口 migration makespan；否则它更适合作为系统实现章节，而不是第三项核心设计。

三个模块的递进关系因此是成立的，但接口必须非常明确。One-Release 应交付一种 canonical migrated state，以及它的预估质量、计算和 I/O 成本；Continuous 在此基础上决定这个状态是否还能继续便宜迁移、当前 debt 是否可接受、是否需要更强 repair；Runtime 则把这个 per-user transition plan 变成不包含隐藏全量工作的原子执行。整篇论文最终需要证明的其实是三个连续命题：第一，推荐 Transformer 的版本失配确实能够在 reader 功能边界被紧凑表示；第二，这种紧凑状态经过连续版本更新后仍然闭包且误差有界；第三，逻辑上的低成本迁移能够真实转化成低 bytes、低 GPU 时间和短 migration makespan。下一轮最有决定性的工作不是继续发明更多原语，而是先完成 PRO residual 的校准分解、与通用 tail/token/KV mapping 的等预算对比、两跳和多跳迁移的状态闭包实验，以及 Medium/Large 上的 migration roofline。它们会直接决定三个模块各自真正应该设计什么。
