## 原始任务书（逐字保留）

~~~text
# EvoKV 专家头脑风暴：背景与讨论任务

我们研究的是持续模型更新下的推荐用户状态迁移问题。在基于 HSTU/Transformer 的生成式推荐系统中，模型会不断训练并发布新版本，但每个用户的大量历史已经被旧模型计算成 persistent KV state，并长期保存在系统中。新模型发布以后，如果继续直接读取旧版本生成的状态，会损失新模型本来能够获得的推荐收益；但如果把所有用户的完整历史都重新用新模型计算一遍，又需要巨大的 GPU 计算和状态 I/O。因此，EvoKV 想解决的核心问题非常明确：**在模型已经确定发布之后，怎样以远低于完整 KV recomputation 的成本，让海量旧用户状态迁移到新模型，同时尽可能接近 Current Exact 的推荐质量。** 我们关心的不是模型什么时候应该 release，也不是一般意义上的 KV cache 压缩，而是长期存在的推荐用户神经状态如何随模型版本持续演化。

目前我们已经建立了 Small、Medium、Large 三个规模。Small 使用约一万用户、4 层 HSTU 和 512 context，主要承担机制发现、反例分析和设计原型验证；Medium 使用约三万用户、6 层模型和 1024 context，已经完成训练，整体上能够复现 Small 中观察到的核心问题和结构；Large 正在进一步训练，用于检验这些现象和未来设计在更大的模型、用户人口和 persistent-state footprint 下是否继续成立。在 Small 上，我们已经得到了一版轻量的单边迁移原型：它不重新生成完整的 Current KV cache，而是在 HSTU reader 的聚合边界上，为每个用户计算一份紧凑的 reader compatibility correction。当前 lightweight PRO 的公平理论计算量约为 Exact-All 的 **9.1%**，只额外保存约 2 KiB 的用户级 sidecar。 在冻结配置后的五条 release edge、217,584 个真实 rolling 请求上，它相对直接 Reuse 的 AUC **5/5 都有提升**，五条边平均 AUC 和 log-loss 也都改善，但不同版本边上的恢复幅度差异仍然较大，log-loss 只有 3/5 正向。因此，目前可以确认的是这条路线确实可行，但还不能认为单边迁移的最终设计已经完成。

接下来整篇论文准备围绕三个递进模块展开。第一个模块是 **One-Release Migration**，研究一次 Parent→Current 版本切换时，究竟应该迁移什么，才能以很低的计算成本获得尽可能接近完整重算的推荐质量。这里最重要的要求是，最终方案不能退化成一个普通的 Transformer KV repair，例如简单重算 tail、选择几个重要 token 或做通用的 K/V mapping；我们希望从真实 HSTU 推荐实验中发现 recommendation + Transformer 共同作用下的特殊结构，再由这些 Insight 推导出真正有推荐系统辨识度的迁移机制。现有 PRO 可以作为这一方向已经取得的一个重要结果，但这一轮希望专家进一步思考：单边迁移最本质的问题到底是什么，正确的迁移对象或者功能边界应该在哪里，10%–20% 左右的 Exact 计算预算应该达到怎样的质量恢复才足够有说服力，以及现有设计还缺少什么关键结构才能成为论文真正的第一项核心贡献。

第二个模块是 **Continuous Multi-Release Migration**。即使一次近似迁移能够工作，真实系统还会持续经历 \(v_0\rightarrow v_1\rightarrow v_2\rightarrow\cdots\)，因此必须回答一个更本质的问题：这种近似连续执行以后，为什么不会越来越差？我们希望这一部分最终不是大量工程规则的堆砌，而是找到一个简单、可信的长期状态演化原则。专家需要帮助我们判断，连续迁移中最核心的风险究竟是什么；算法本身应该提供怎样的误差约束、状态债务上界或收敛机制；什么时候可以继续便宜地增量迁移，什么时候必须进行更强的 repair 或重新建立 Exact 状态；以及 sampled Exact、真实行为反馈、Rebase 等反馈机制应该承担什么角色。理想状态下，这一部分形成的是一个清楚的“算法保证 + 反馈闭环”，使单边近似能够成为长期运行的状态管理机制，而不是简单地每隔几个版本轮流全量重算。

第三个模块是 **GPU Migration Runtime / Migration Kernel**。前两个模块解决“应该计算什么”，这一部分解决“怎样真正把这些计算高效地跑在大规模用户上”。理论 FLOPs 很低并不意味着真实系统一定很快，因为还存在 persistent-state 读取、raw-history I/O、不规则 batch、GPU utilization、kernel launch、写回以及 migration 与在线 serving 的资源竞争。因此这一部分需要研究，如何把大量具有不同历史长度和迁移配置的用户任务组织成高吞吐 GPU batch，怎样做 bucketing、sharding、prefetch 和流水并行，是否可以把 reader transformation、aggregation 和 sidecar generation 融合成专门的 migration kernel，以及算法上的计算节省最终能否真正转化成更高的用户迁移吞吐、更低的状态 I/O 和更短的全人口 migration makespan。

因此，这一轮专家头脑风暴的目标不是马上替我们给出三个具体算法，而是先帮助我们把这三个模块各自最值得解决的问题确定下来。我们希望专家站在论文整体的高度思考：**One-Release 最核心的研究问题是什么，什么才算真正具有推荐 Transformer 特征的迁移设计；Continuous 最核心的正确性问题是什么，什么样的简单机制足以保证长期演化可信；GPU Runtime 最关键的物理瓶颈是什么，怎样才能形成真正有技术内容的系统贡献。** 同时还需要判断三个模块之间应该怎样递进、每一块最重要的一句话原则是什么、什么实验结果才意味着这一块已经真正解决，以及完成这一块之后应该向下一块交付什么。最终希望这一轮讨论形成的是一张清楚的研究地图，而不是一组零散优化：先确定我们真正需要回答的问题，再由这些问题去指导后续 Insight、Design 和实验。
~~~

## 专家思考结果

我的总体判断是，这三个模块不应被组织成三个并列的优化主题，而应被统一成同一个“版本化 reader contract”的三个层次。One-Release 回答旧状态在 Current reader 看来应该表达什么，Continuous 回答这份近似表达跨版本为什么始终可信，Runtime 回答如何把这种状态更新高效而且原子地施加到整个人口。论文最强的主线不是“修复一批旧 KV tensor”，而是“旧 persistent KV 是一份由 Parent 生成、供 Current 消费的过期用户证据契约；EvoKV 迁移的是它对 Current reader 的功能作用，长期维护的是这种作用的可信边界，Runtime 则负责以一次流式状态转换兑现它”。这样，三个模块分别解决语义正确性、时间正确性和物理可行性，不会散成 KV repair、Rebase 规则与 GPU batching 的拼盘。

One-Release 最本质的问题并不是哪些 token、K 或 V 最值得重算，而是 Parent→Current 的 reader mismatch 在真实推荐 query 分布上究竟有多低维。设 Current Exact 的目标功能是 Current reader 使用 Current history state 对真实请求和候选进行读出，EvoKV 并不需要构造一份在 tensor distance 上接近 Current KV 的新状态，而只需要找到一份紧凑的用户级兼容对象，使 Current reader 在 Parent state 加这份对象上的功能输出接近 Current Exact。换句话说，正确的迁移对象应是 Current reader 对旧用户证据的功能修正，而不是新版本历史 K/V 的近似副本。当前已经定位到的 `activated(qK)·V` 或 AV 聚合边界非常有价值，因为它是历史状态第一次以候选 query 为条件形成最终证据贡献的位置；但最终持久对象未必永远是一条 AV vector，它也可能是一个很小的、由真实 request context 条件化的 reader operator。

真正具有 recommendation + Transformer 辨识度的设计应同时利用三个事实。第一，同一用户状态会被一整个 candidate bank 反复读取，因此迁移生成成本应主要按用户支付，消费成本应在候选集合上摊销，而不是为每个 candidate 执行 token repair。第二，这份状态还会被发布后的多个真实请求持续消费，因此它必须具有跨请求稳定性和明确的 rolling 生命周期，而不只是修复 cutover 时的一次 query。第三，HSTU 的非归一化聚合意味着用户状态不仅包含向量内容，还包含 evidence coverage、multiplicity 和 mass；压缩或重组历史时，raw item identity 不能代替功能可合并性。这三点共同构成了 EvoKV 与一般语言模型 prefix repair 的分界。如果一个方法拿掉 candidate-bank reuse、长期用户状态和 evidence-mass 语义后仍可原样成立，那么它还不够 recommendation-specific。

现有 PRO 已经证明这个方向确实存在，但当前 C32 更像 reader compatibility function 的一阶近似，而不是最终表示。它以约 9.1% Exact FLOPs、约 2 KiB sidecar 在五条 edge 上获得 AUC 5/5 正向，这是很强的 viability evidence；但按五条正式结果等权计算，AUC Reuse harm recovery 约为 34.7%，其中一条 edge 只恢复约 3.3%。最新 progressive 结果又显示，两条同类 probe 几乎完全冗余，单纯校准幅值、区分 old/recent decay 或增加同构 carrier 都没有形成稳定、单调的 precision frontier。C64 相对 C32 的内部 relative L2 有一致改善，并不等于已经找到了更高精度的可部署动作，因为 absolute rolling direction 没有过门，C48/C64 也不单调。这说明缺失的不是一个更好的 scalar，而是 Exact reader correction 中尚未被当前 estimator 表达的功能方向和 rolling transport structure。

因此，One-Release 下一项最有价值的 discovery 不是继续枚举 carrier、tail region 或 probe item，而是直接测量 Exact reader correction 在“release、用户、请求上下文、候选、层”几个轴上的条件秩和方差分解。最关键的诊断问题是：一个请求内部是否接近 candidate-shared；跨真实请求后需要增加多少 request-context component；不同层是否共享同一组功能方向；剩余 candidate residual 是否小到可以安全忽略。可以把 correction 理解为 release-shared component、user-specific component、request-context component 和 candidate residual 的组合，并在 held-out 的真实 exposed candidate bank 上测量每增加一个 component 能解释多少 Exact gap。这里读取 Exact correction 只用于机制诊断和 prospective design，不应拟合 target K/V，更不能把旧五边 quality label 重新用作新方法资格。若最终稳定秩为一，现有 PRO 的论文叙事会非常漂亮；若秩是很小的二到四，也仍然可以形成 compact reader operator；若在 20% 预算内仍然是高秩且强烈依赖 candidate，则应尽早承认低成本统一迁移的边界，而不是继续用复杂 selector 掩盖问题。

One-Release 还缺少两个面向下一模块的关键结构。一个是 sidecar 的 transport law：发布时生成的 correction 中，哪些成分是持久的版本差异，哪些成分应该随着实际 Current append、old-state eviction 和 request context 改变而被减去、替换或失效。已有结果不支持把自然 append 或一个 global coverage scalar 当成普遍收敛规律，简单的 old/recent segment decay 也没有稳定过门，因此必须从 reader contribution 和真实 cache lineage 中寻找可执行的更新语义。另一个是可加强而且有序的精度阶梯。Continuous 的 Warning 状态只有在“增加预算确实更安全”时才有意义；当前 C32/C48/C64 并不满足这个条件。最终要么构造 nested refinement，使高预算计划是在低预算结果上添加新的 residual，而不是重新估计一份可能变差的 sidecar；要么诚实地只保留 `Reuse/PRO/Exact` 三档，PRO 低置信时直接 Exact，不把中间 carrier 数包装成 stronger repair。后者虽然简单，却比一个没有单调性证据的多档 controller 更可信。

对于 10%–20% Exact 计算预算应该达到的质量，我会把当前 C32 定义为“路线成立”，而不是“问题已经解决”。建议性的论文完成门槛是：约 10% 预算应平均恢复至少 50%–60% 的正向 Reuse harm，并在绝大多数合格 edge 上产生实质恢复；约 20% 预算应达到约 75%–80% 的平均恢复，同时形成事前冻结的单调功能精度改善。最终部署策略还应结合 label-free admission，使低置信 edge 回退到 Reuse 或 Exact，而不是要求一个固定 PRO 无条件用于所有 release。这个门槛不是数学定理，但反映了贡献强度：如果使用 Exact 五分之一的计算仍只恢复约三分之一损失，PRO 更像优秀原型；如果能恢复四分之三以上，同时保持极小 sidecar 和 candidate amortization，就足以成为论文第一项核心贡献。

质量评价也需要保持逻辑一致。`Reuse harm recovered`、PRO 与 Reuse/Exact 的绝对 AUC 差、成对置信区间和 edge-equal aggregate 应作为主要口径，不应把 Full-only gain 很小时高度不稳定的 release-gain retention 当作唯一 headline。Current Exact 是状态语义参考，却不一定在每个 companion metric 上都是上界；例如某些 edge 上 Current Exact log-loss 本身差于 Reuse，此时不能同时要求迁移方法在功能上趋近 Exact、又在该指标上必然优于 Reuse。已经封存的严格 gate 应继续保留原始 FAIL 裁决，未来 prospective contract 则应明确区分 reader-function fidelity、模型发布时选定的 primary ranking utility，以及 companion metric 的安全 margin，不能看到旧结果后回改规则。One-Release 最终向 Continuous 交付的也不应只有一份 sidecar，而应是一组冻结的 transition semantics、rolling transport 或 expiry rule、target-free confidence certificate、Exact fallback 和分项 cost vector。

Continuous 最核心的正确性风险不是“每一版误差简单增加一点”，而是上一版的近似状态会成为下一次迁移的输入，一些在当前请求和候选上不可见的误差可能被后续模型变化放大，直到未来 query distribution 出现时才暴露。因此 one-hop fidelity、producer age、固定 approximation depth 和自然 eviction 都不能单独构成长期保证。特别是已有 controlled dilution 中存在反例，不能把 Current append 默认成 contraction。连续模块真正需要管理的是 recursive approximation 的可观测性和放大性：本次迁移产生多少新 residual，已有 residual 经过下一次版本变换后会被衰减还是放大，以及当前 sampled query 是否覆盖了可能在未来出现的风险方向。

我建议把长期状态演化原则浓缩成“Anchor、Account、Audit、Rebase”。每条 lineage 始终指向最近一次 Exact 或 Rebase anchor；每次近似转换都消耗一部分有上界的 compatibility debt；sampled Exact 持续审计和校准这个 debt certificate；一旦证书失效、上界超过阈值或近似深度达到硬上限，就重新建立 Exact anchor。这里的 debt 不应只是一个 predictor 的点估计，而应是按 lineage stratum 维护、包含统计不确定性余量的 reader-functional error 上界。可以研究一个简单递推：下一版 debt upper bound 等于已有 debt 乘以一个局部 amplification upper bound，再加本次计划引入的 one-step residual upper bound 和 shadow sampling uncertainty。如果 amplification 无法被可靠估计，就不能声称 debt 能安全传播，只能依靠更保守的 depth hard cap 和更早 Rebase。

Sampled Exact、真实行为反馈和 Rebase 在这个闭环中应承担完全不同的角色。Sampled Exact 是即时传感器，用 normalized score gap、Bernoulli JS、Top-K overlap 和 margin disagreement 等无标签信号比较 approximate 与 Current Exact，并为每种 source age、approximation depth 和 plan lineage 校准误差上界。为了兼顾时间可比性和人口覆盖，可以保留一个固定 shadow panel 观察持续漂移，同时轮换一部分按 lineage 分层抽样的用户，避免固定样本逐渐失去代表性。真实行为反馈是较慢的配置级审计器，用来验证无标签 fidelity proxy 是否仍对应真实 AUC/log-loss，并在后续 release 全局失效某个配置；它不能成为同一请求或单个用户的 future-label scheduler。Rebase 是证书失效后的 reset actuator，不应被包装成默认每隔几个版本全量重算；固定周期 Rebase 应是 Continuous 必须击败的强基线。

Continuous 可以提供的可信保证不是“每个用户的 AUC 永远不下降”，因为有限 sampled Exact 无法在没有额外假设时证明这一点。更合理的是一个 population/stratum-level probabilistic invariant：在明确的抽样与分布条件下，每次 release 后各 lineage stratum 的高分位 reader debt 以至少预定置信度低于阈值，并且任意 lineage 在至多 H 次近似之后重新建立 Exact anchor。这是 bounded safe set，而不是渐近收敛定理。实验必须执行真实 recursive lineage，让前一版近似输出成为后一版输入，并在每一版保留 Exact reference；不能把多条 direct one-hop 结果拼接成 continuous evidence。主要比较应包括每版 Exact、无反馈连续近似、age/depth-only、最佳固定周期 Rebase，以及 debt-bounded 加 Exact-shadow feedback。只有当每版尾部和最坏 lineage debt 都保持在预注册 envelope 内、shadow 能及时捕获失效、且在相同质量约束下总成本显著优于最佳固定周期 Rebase时，这一模块才算真正解决。如果需要很高 shadow rate 或频繁 Rebase 才不越界，那么 controller 只是隐式周期重算，还没有形成独立贡献。

GPU Runtime 的核心问题也不应被表述成“怎样把 9% FLOPs 跑得更快”，而是“算法把计算削减之后，新的物理下界究竟是什么，以及能否让每个必要的状态字节只流动一次”。对固定 probe 的 `qK` 和 activated-weighted `V` reduction 粗略只有 order-one FLOP/byte，很容易变成 storage、H2D 或显存带宽受限；32/64-carrier 的 Current replay 又可能因为问题太小而受到 kernel launch 和 occupancy 限制。除此之外，还有每用户小 sidecar 对应的大量 metadata 操作、迁移与 serving 争用 GPU/PCIe/state-store 带宽，以及 migration snapshot 与 post-cutover append 的一致性问题。理论 FLOPs 下降只说明潜在算术收益，并不说明这些物理成本已经下降。

这里尤其要正视 PRO 和 Exact 的 I/O 结构并不相同。Exact 通常读取紧凑 raw history、执行完整 Current 重算并写出完整 Current KV；PRO 则读取完整 Parent KV、少量 recent history、执行轻量 reader transformation 并只写 sidecar。PRO 显著降低计算与写回，但如果仍需扫描全部 Parent K/V，就不能先验声称 source-state read 也更少。Large 满状态约为 12.5 MiB/user、全人口上限约 972.7 GiB，而 sidecar 约为 12.8 KiB/user，写回量具有接近三个数量级的优势，但全量 Parent-state scan 仍然是硬成本。因此 Runtime 的第一个实验不是直接写融合 kernel，而是建立真实 stage-by-stage roofline：分别测 state-store read、CPU decode、H2D、reader reduction、carrier replay、sidecar write、metadata commit 和 serving interference，判断整个系统究竟被哪一项限制。

如果 profiling 证明方案具有物理空间，真正有技术内容的系统贡献应是一个 read-once transactional transformation engine。它按照 source/target version、state shard、sequence length 和 plan signature 组织接近顺序的状态读取，用 pinned double buffers 重叠 storage、H2D、GPU compute 和 writeback；在 GPU 上把 reader-pushed version transform、`qK`、activation、weighted `V` aggregation、mass/coverage handling 和 sidecar layout 尽可能融合，不物化 translated prefix K/V，也不写无用中间状态；对小而 ragged 的 Current carrier replay 使用长度 bucketing、segmented execution 或 persistent scheduling 减少 padding 和 launch 浪费。更重要的是，Runtime 必须实现版本一致的 COMMIT：后台 migration 只能基于明确的 state epoch 生成结果，cutover 后发生的新 append 不能被旧 snapshot 的写回覆盖，可以通过 delta catch-up、compare-and-swap 或等价事务语义解决。只有吞吐而没有这一一致性协议，仍不是完整的 persistent-state migration runtime。

Runtime 的成本模型还应反馈给 Continuous，而不是永远单向下游。一个计划的实际 makespan 近似由 state-store bytes/带宽、H2D bytes/PCIe 带宽、算术量/GPU 吞吐和 write bytes/存储带宽的最大项，再加 commit overhead 决定。Continuous 最终应使用 Runtime 提供的真实 service curve 选择计划和 migration deadline，而不是用一个任意加权的 FLOP 分数代替物理成本。Runtime 是否成为独立系统贡献，应由完整人口、真实长度分布和真实 state store 上的 end-to-end 结果判断，并与 competent batched PyTorch 或通用 kernel baseline 比较，而不是只击败逐用户 Python。作为建议性论文门槛，Large 端到端 makespan 相对 Exact 应达到约四倍或更高的量级改善，并接近实测 pipeline roofline 的大部分，同时专用 Runtime 相对朴素 PRO 仍有显著增益、serving p99 干扰在预注册范围内、failure injection 和 concurrent append 下没有 lineage corruption。如果 9% FLOPs 最终只转化成不足两倍的 makespan 改善，那么最重要的系统结论是 state scan 已成为新瓶颈，下一步应反向要求算法减少 Parent-state read，而不是继续优化只占小部分时间的 CUDA kernel。

三个模块之间最终应形成非常具体的交付关系。One-Release 输出一次可执行的 reader-functional transition、sidecar 和 transport semantics、目标无关的置信证书、合法 fallback 以及 GPU work、raw-history I/O、state I/O、write bytes 和 storage 等分项成本。Continuous 不重新打开 token selector、semantic group、K/V mapping 或 per-candidate route 等操作目录，只在冻结 transition 之间维护 anchor、depth 和 debt certificate，并输出带 lineage、deadline、plan mix 与 commit invariant 的执行流。Runtime 负责将这些 typed plan 变成可恢复、版本一致的状态提交，同时把真实吞吐和服务曲线反馈给 controller。这样三个模块依次回答“迁移什么”“为什么长期可信”“如何真正执行”，且每一块都有明确的上游假设与下游交付物。

从当前证据出发，最合理的研究顺序是停止在同一 Small/seed17 五边上继续调整 PRO，把 C32 保留为已经证明结构路线成立的正式主设计和 Continuous focused probe 的候选动作；在新的 prospective evidence 上优先验证 Exact reader correction 的最小功能秩、跨请求 transport 和 label-free confidence，而不是继续增加相似 probe 或 carrier；在有序精度阶梯尚未建立前，Continuous 先使用简单的 `Reuse/PRO/Exact`，不要把 C48/C64 称为 guaranteed stronger repair；Medium 和 Large 只承担冻结 Insight 与机制的 prospective scale qualification，不作为新的调参集；Runtime 可以提前进行只读 profiling 来检验物理可行性，但完整 kernel 工程应等待真实瓶颈明确。这个顺序既保留了现有结果的价值，也能让下一轮实验直接回答论文最危险的未知量。

最后可以为三个模块各设一个清楚的失败判据。若 Exact reader correction 在真实请求上是高秩且强 candidate-dependent，或者 20% 预算仍无法恢复大部分 Reuse harm，那么 One-Release 的统一 compact reader-object 假设需要收缩；若 Continuous 只有依赖高 shadow rate 或频繁 Exact Rebase 才能维持质量，它就没有优于固定周期策略；若 Runtime 被不可避免的 state scan 完全限制，端到端相对 Exact 只有很小收益，那么系统贡献不能只靠 kernel fusion 成立，算法本身必须减少读取字节。这三个 falsification gate 与成功门同样重要，它们能阻止研究在已经失去主假设后继续堆叠局部优化。

整篇论文最终最重要的一句话原则可以保留为：One-Release 迁移的是 reader 对用户证据的作用，而不是 KV tensor；Continuous 让每次近似都从最近的 Exact anchor 消耗一份可审计的 debt budget；Runtime 让每个必要状态字节只流动一次，并且只提交版本一致的结果。如果这三句话分别获得语义、长期和物理证据，EvoKV 就会形成一张完整的研究地图，也会成为一篇关于 persistent recommendation neural state evolution 的论文，而不仅是一套低成本 KV 修补技术。
