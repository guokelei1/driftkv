# 当前研究状态与路线

更新日期：2026-08-11。

## 1. 研究问题

模型按时间窗口连续更新为 θ1、θ2、…；线上只使用一个当前模型 θt。若用户前缀 K/V 仍来自旧模型 θs，系统可以直接 Reuse，也可以用 θt 完整 Recompute。本文要研究二者之间可利用的精度—开销空间，并据此设计比全量重算便宜、比直接复用准确的维护方法。

第一步不是优化维护算子，而是建立一条真实、可重建、重复出现 Recompute 优于 Reuse 的大模型版本链。该基础现在已经具备。

论文动机所需的质量与成本证据已精简汇总在 [09_motivation_observations.md](09_motivation_observations.md)。

## 2. 已选第一轮基线

数据与时间：

- KuaiRand-1K standard log；random-exposure log 不参与训练或评测。
- 2022-04-08 至 2022-04-21 构造 θ0。
- θ1–θ8 分别使用 04-22 至 04-29 的当天数据更新，并在各自下一自然日评测。
- 更新日目标不会进入同一版本的预测集；历史、正样本和候选集合均按 [评测协议](eval_protocol.md) 固定。

模型与目标：

- 8 层 HSTU，hidden size 512，8 heads，最大序列长度 512。
- video 与 author 两个字段，`latest_item_query`，归一化 sampled-softmax next-item 目标。
- 自然模型为 6,033,893,120 parameter bytes（5.620 GiB）。
- 冻结日窗口训练日程为：θ1/θ2 各 4 epochs；θ3 2 epochs；θ4 3 epochs；θ5/θ6/θ7 各 2 epochs；θ8 3 epochs。每个版本最多使用 20,000 个更新样本，具体学习率由冻结配置逐版本给出。

大模型容量：

- 使用 `strided_hash_v0` 将物理 embedding 容量扩至自然语义空间的 8 倍，只有一份 embedding，不使用相同副本伪造容量。
- 23,396,297 个物理行中，2,924,537 行可由当前 trace 访问；其余 20,471,759 行是不同的冷 catalog 行。
- 真实可达行、dense core 与 projection 从自然链逐元素搬运，最大 active-row 误差为 0；冷行只增加容量，不改变当前请求的函数。
- 每个版本为 47,960,055,552 parameter bytes（44.666 GiB），每份完整 checkpoint 为 48,077,080,276 bytes；模型必须在 GPU0/GPU1 两卡分片执行。
- 大模型推理得到的 28 个格与自然链完全一致。这证明扩容没有改变任务函数，但不证明冷行本身提升了推荐质量。

## 4. 当前热 HBM 核心耗时

当前成本端点为 `hot_hbm_hstu_core_only`。模型、请求 embedding 与旧前缀 K/V 在计时前已经驻留 GPU；Reuse 计算固定两-token suffix，Recompute 计算完整序列，两端都物化完整目标 K/V。模型/checkpoint 加载、源 cache 生成、CPU→GPU 传输、embedding lookup、候选打分、质量指标和写盘均不计时。CUDA event 逐批计时，双卡逐批取较慢 rank，方法顺序交替。

真实 θ8←θ7 checkpoint 校验使用 32 个自然请求，Reuse 为 `9.093 ms`、Recompute 为 `63.535 ms`，即 `6.987×`。单模型正式锚点使用同一个 44.666 GiB θ8 checkpoint、512 tokens、256 个 synthetic timing requests 与 global batch 16，Reuse 为 `72.044 ms`、Recompute 为 `504.095 ms`，即 `6.997×`。这里的约 `500 ms` 是 256 个请求顺序组成 16 个 batches 的总时间；`1.969 ms/request` 是吞吐摊销，不是单请求独占 GPU 的 latency。

### 4.4 一千万用户的一次迁移卡时

人口级规划固定 `10,000,000` 用户和 A40。44.666 GiB 全局模型保持两卡 embedding 分片、每卡复制 HSTU core；每卡分别假设模型和运行时之外有 10/20 GiB 可用于 K/V。长期 cache 按 FP16 计算，单用户字节为 `2(K/V) × layers × tokens × hidden × 2`；执行 admission 按当前 FP32 消费端的 source+target 双缓冲并保留 10% 余量。实测 local batch 8 是保守吞吐校准点，不宣称为全局最优 batch。卡时先由双卡 rank-max CUDA 时间换算为单卡工作量，再把理想热内核卡时除以 70% sustained efficiency 得到规划值；该 70% 是显式容量规划假设，不是新测量。

下表卡时写作“70% 规划值（理想热内核下界）”。C2/C4/C6/C7 直接引用 40 点实测；C8 用同一实测表中的 H512→H1024 方法特定宽度倍率作用于 24L/H512/S2048 点，是标记清楚的 factorized planning estimate。

| ID | layers / hidden / tokens | HSTU core | FP16 K/V / 用户 | 1000 万用户 K/V | 10/20 GiB 驻留用户 | FP32 双缓冲 batch 10/20 | Reuse A40 卡时 | Recompute A40 卡时 | 比值 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| C2 | 8 / 256 / 512 | 10.8 MiB | 4 MiB | 38.1 TiB | 2560 / 5120 | 8 / 8 | 2.04（1.43） | 6.58（4.61） | 3.23× |
| C4 | 8 / 768 / 512 | 94.0 MiB | 12 MiB | 114.4 TiB | 853 / 1706 | 8 / 8 | 2.34（1.64） | 24.71（17.30） | 10.55× |
| C6 | 16 / 512 / 1024 | 83.2 MiB | 32 MiB | 305.2 TiB | 320 / 640 | 8 / 8 | 4.80（3.36） | 106.59（74.61） | 22.23× |
| C7 | 24 / 512 / 2048 | 124.3 MiB | 96 MiB | 915.5 TiB | 106 / 213 | 8 / 8 | 11.89（8.32） | 579.87（405.91） | 48.77× |
| C8* | 24 / 1024 / 2048 | 490.4 MiB | 192 MiB | 1831.1 TiB | 53 / 106 | 8 / 8 | 13.51（9.46） | 1306.91（914.84） | 96.70× |

在这五组里，10 GiB 最差仍能按 FP32 source+target 和 10% 余量 admission 12 个用户，因此没有把 local batch 8 压低；增加到 20 GiB 只扩大驻留 cohort，不改变热内核卡时。10 GiB 只有在单份 active FP32 K/V 超过约 576 MiB 时才会把该双缓冲 batch 压到 8 以下，20 GiB 的对应边界约为 1152 MiB；当前最大 C8 为 384 MiB。这里 Recompute 的主要瓶颈是完整序列 HSTU attention 计算，Reuse 的主要瓶颈是旧 K/V 读取、拼接和目标 K/V 物化。1000 万份 cache 必须分 cohort 搬运；DRAM/SSD ingress、跨卡通信和排队未计入，不能把本表称为端到端迁移时间。

这些结果全部是 `scientific_result=false`、`formal_result=false` 的开发级微基准，不是端到端服务延迟。冻结配置为 `configs/evokv_d1/development/kuairand_large_hotkv_scaling_20260811_v0.json`，40 点结果为 `results/design1/kuairand_large_hotkv_scaling_20260811_v0/full/result.json`，详细边界见 [评测协议](eval_protocol.md)。

## 5. 为什么这条链可以作为第一轮 baseline

它满足当前机制开发所需的四个条件：连续自然日更新、所有相邻边都有正空间、跨版本通常会累积、物理参数超过单卡容量。评测是在真实两卡大模型上执行，而不是把中模型数值手工复制进表；容量 lift 的函数保持性质和两侧数值相等都由结果与验证器记录。

它仍然只是 `scientific_result=false`、`formal_result=false` 的单 seed 开发基线。论文正式结论还需要独立 seed、置信区间和冻结后的跨数据集确认。当前不能宣称损失必然随 age 单调，也不能宣称 44.67 GiB 模型比 5.62 GiB 模型质量更好。

## 6. 已淘汰的做法

- 不再用人为 K/V 坐标变换、手动乘倍数或事后改候选数制造矩阵。
- 不再以两层小模型或随机逐版本“抽卡”作为大模型结论。
- 不把 Recompute 强行设为每格质量上界，也不删除不利格子。
- 不继续维护互相冲突的旧路线文档；需要历史时以 git 历史和紧凑结果为准。

## 7. 下一步

当前目标已经从“继续寻找 baseline”正式切换到“在冻结 baseline 上开发 D1”。D1 不是再算一张 8×8，而是从 θ0 精确 cache 出发，按 θ0→θ1→…→θ8 维护一条真实递归轨迹；θ0 后不允许隐藏的 Full Recompute reset。θ0→θ1 是 bootstrap 诊断，现有 8×8 支撑的主证据边是 θ1→θ2 至 θ7→θ8。完整契约见 [Design 1 单链路线](10_design1_recursive_route.md)。

先冻结这条链作为机制开发输入，不再为美化矩阵重训。下一阶段只做：

1. 冻结与 qualification query 分离的无标签 fit/development 记录；
2. 先完成 θ0→θ1、θ1→θ2 canary，再验证不复位的 θ1→θ2→θ3 递归 prefix；
3. 选定候选后一次执行到 θ8，逐边报告绝对质量、gap recovery、lineage、迁移量、理论工作量与单独实测的 GPU 成本；
4. 机制稳定后再做独立 seed 和正式协议，不把当前开发选择当作独立重复；
5. 模型文件丢失时严格按 [基线复现说明](BASELINE_REPRODUCTION.md) 重建，禁止从旧实验路径拼装 checkpoint。
