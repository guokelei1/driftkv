Implementation的目标是在代表性规模、相同资源条件下把完整计算节省转成实际时间／吞吐收益，
并非要求每个请求都快于Rebuild。共享固定成本可以摊销，逐行转换和逐请求开销仍须优化实测。

用户进一步明确：4人甚至4096人的计时都不是最终规模裁决，30k账本也只是现有实测事件
分布的参考点；先推导规模曲线与盈亏平衡，再确定足以检验主张的规模。以同一发布周期为
单位，扣掉两边公共工作后，Rebuild为`N·R`，本方法为`S+N·C`。S包括纠正校准及共享准备，
C包括码准备、全周期额外读写与交接；仅当C<R时才存在`N>S/(R-C)`的时间盈亏点。
时间与FLOPs分别建模，不能用峰值TFLOPs直接换算。基础模型训练是双方共同成本B：
加入后绝对节省不变，但总体训练＋服务的百分比需要重新计算，现有30.18%不是该完整口径。
目录、拟合人口、副本数、内存层级和请求频度改变时，S和C也随之更新。

目标证据为规模增长下的质量—总时间曲线，并与持续保留状态的部分重算／预算重建比较。
相近预算下恢复更好是待验证主张，不是预设结果；不能只比较一次码生成和一次重建，漏掉
随后重复纠正读取。方法质量／工程检查按[多组计划](cross_group.md)覆盖不同模型和早中晚
版本，未完成适配／校准的模型组只能提供原生形状证据。

起点为 `A_itemgate6_rms_roll4`：候选物品门控、每层每行共享 12＋每头私有 6，
当前每头读共享 3＋私有 3；原生 K/V 保留，纠正读取参与行为写入；
码更新采用可合成递推和单缓冲区锚码接续。
Medium 为 6 层、192 隐维、6 头，窗口 1024，V2→V3→V4→V5。
后续每版校准实际为 64 fit／16 validation、local8／joint4、4 步续写；
首版已有起点和固定特征来源继续单独计费。旧 rank8／support flag 方案仅为历史参照。

已完成的[方法证据](../../results/query_relay_2026_10/report.md)和
[工程复验](../../results/implementation_2026_10/report.md)直接复用。
动态／独立静态 writer 的 4096＋1024 比较、均值门控、已完成的核与状态数值检查不重复排队。
原反馈约 65.89% 恢复及其成本边界继续保留；next-item 的高恢复比率不能解释为精确还原教师。

## 第一批执行范围

1. **资产清单（CPU）**：核对当前模型、候选、面板、用户角色和已完成证据，保留真实可用路径。
2. **真实 32 用户 trace（CPU）**：复用既有工程面板，生成 next-item16/16 与原反馈的事件序列摘要。
   检查推荐分组、同时间事件次序、逻辑时间与到达时间分离。这不是新的质量实验。
3. **服务接入**：trace 已接到 `RelaySession`／原生会话，四用户双协议评分与状态验证已通过。
   接着跑小面板真实到达队列，再扩固定 128／512 用户驻留集。
   不直接把旧按用户顺序执行的集成脚本耗时、显存当作在线指标。
4. **质量／基线／跨条件（独立任务）**：在 Q/B/X 各自的实际设置准备好后执行小探针；
   第一轮不重训基础模型，不重跑已完成控制，不为补数量增加全组合实验。

CPU trace 和合成排队检查仅验证事件与计时逻辑。真实GPU到达pilot仍采用四用户与全版本共驻，
只作有限负载诊断；生产尾延迟、稳定吞吐与容量结论需要后续独立测量。

## 共同评测口径

- 原反馈与合成 next-item 是不同任务，分别保留标签、质量、基线、事件账。
  next-item 当前起点是每 16 次原始行为触发、每轮 16 候选；未知目标等过滤可能改变有效比例。
  stride8/32、候选2/16是负载敏感性，不按恢复率选择后宣称生产事实。
- 按相同发布的 AUC 差先平均再计算恢复率，报告绝对差和用户配对区间；
  不平均各版恢复百分比，不隐藏不利版本。质量、校准、部署人口分别注明。
- 4096 人是开发人口；两批已揭晓的 1024 确认均不再作为新的盲确认。
  校准／验证和历史保留角色继续隔离，最终确认另选未揭晓用户。
- 一次重建主参照是每用户每版首次推荐重建，然后正常增量并保留状态。
  每请求 Fresh 只作诊断；及时行为服务下的首次历史消费重建另列敏感性。
- 全部校准、教师及必要来源准备、完整物品表、码准备／交接、行为和查询新增工作计费。
  分别报新增／一次重建预算、完整服务净成本、额外读取／原生 query 和 attention。
  改变请求频率或行为推进规则后重新计账，不套用旧 17.3261% 比例。
- 时间验证与完整成本范围对应：共享准备和服务分别实测，记录资源数量、批处理与并行方式；
  不把重叠阶段的耗时简单相加当作墙钟完成时间，也不把提前执行的工作算作免费。
  四用户arrival未计校准及目录生成，它的局部慢点不能解释为训练费用尚未摊薄。

## 服务语义与资源

第一版保留当前 **on-demand 历史推进**：行为到达事件不立即编码，推荐、发布与结束时
按原会话的严格过去规则推进历史，并保留最多 32 行的追加带。
在同一原始时间戳按发布→推荐→行为处理，保留用户内部原事件次序；候选不写缓存。
及时处理行为是之后单独的变体，不能悄悄混入原轨迹。

逻辑时间决定版本、模型时间间隔和可见历史；墙钟到达时间只控制负载。
缩放到达间隔不改逻辑时间、候选或状态归属。单 GPU worker 顺序调用现有会话，
发布作为屏障；发布期间排队、反锚、首次物化／重建进入相应等待和执行账。
服务指标至少区分冷首读、热读、行为工作与发布窗口，GPU 完成后才停止计时。
原生基线也使用合理优化的后端；共享准备即使移到稳态之外，也单列时间、空间和成本。

每次启动前检查 GPU。先用一张空闲卡跑小检查，训练等独立任务可用其他空闲卡；
实际性能测量不与其他工作同卡争抢。不停止他人进程，不把所有空闲卡自动占满。
无分布式服务、故障恢复、复杂调度平台的建设要求。
