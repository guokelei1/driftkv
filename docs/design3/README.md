## 当前版本：跨路径算子共享初稿

主报告：[可行性实验](../../results/design3/cohort_01/report.md)。论文Design 3已改为“个体化状态管理产生不同路径，但共同模型计算无需按完整路径一起分裂”。

三个机制：区分状态身份与执行兼容性；共同模型读取合并、修正/证据按行选择；结果按原任务归属返回。只接收已就绪任务，不预测请求到达，不修改D2观察或安装策略。初版固定目标、1024历史、单候选，原六层计算每层修正后再进入下一层。

四目标真实快照组成1/4/8任务工作包；模式为预定构造，不冒充自然到达负载。混合4/8任务相对按完整路径分组减少36.3%/25.1%的读工作包时间，同质和单任务无额外收益。最大logit差7.15e-7，冻结筛查比较一致。当前只验证共享读取，不以旧72UID生命周期结果代证新实现。

入口：`scripts/design3/cohort_probe.py`（A40约22秒），`scripts/design3/cohort_report.py`；核心`src/hstu_kvcache/design3/cohort.py`。发布绑定优化作为底层备选保留，新对照使用原三角求解，隔离跨路径组织的作用。不编译论文。

## 1. 中心与目标

Design 1决定如何继续读取实际KV；Design 2决定在哪里观察目标轨迹并更新持久状态；Design 3决定这些操作如何共享计算、移动数据和占用设备。

**中心假设：按输入的变化周期安排计算，把发布共享部分、状态共享部分和请求变化部分分开；在真正消费数据的位置完成小计算，并将昂贵目标工作切成遵守状态依赖的执行块。**

候选名称：State-Lifetime Execution（按状态生命周期组织执行）。核心不是另设一个近似器，而是为同一状态生命周期组织一个共同的执行路径。

目标有三项：减少同状态重复计算和中间结果搬运；把理论上的低增量计算转成端到端时间收益；让少量目标观察不造成其他用户的大范围停顿。速度、吞吐、内存收益均待测，不预报倍数。

## 2. 现有依据与不能提前下的结论

- 论文记录的原基础域eager native subtotal为821.29s，Exact为577.53s：低FLOPs尚未变成时间收益。但该记录并未证明launch、搬运或求解中的哪一项主导，不能拿它当最终部署延迟。
- 基础域有88,860候选、66,640请求组和62,639次dirty刷新，平均每组仅约1.33候选。因此不能把16候选面板的共享收益当成真实负载默认值；跨请求的view复用也可能有限。
- `scripts/design/native_service.py` 已有状态准备接口。`src/hstu_kvcache/design2/evidence.py` 对已有225维坐标 `[x;o]` 做三角求解；`run_excursion.py`取得实际读取响应和检测统计。
- Design 2当前采用的是所选225坐标上的观测几何，不是此前1281维几何的225维状态收缩。两者不可混淆，本设计冻结当前观测几何及其校准。
- `run_bounded.py`维持目标轨迹、按额度决定是否完整推进并读取；目标差异触发响应接管和请求边界KV安装。这些决策语义保持。
- 共享准备里大量工作仍是源/教师前向。服务端优化不会自动省掉这部分成本，发布准备与服务性能要分开报告。

## 3. 机制一：按变化周期准备计算

### 3.1 三种生命周期

|生命周期|可复用内容|何时重新准备|
|---|---|---|
|目标发布|冻结Translator、检测因子、归一化常量、执行布局|模型或拟合坐标变化|
|实际缓存状态|源编码、读取视图、检测的源相关部分|对应依赖发生变化，如摘要、长度、mask、目标变化|
|当前请求|query、native响应、读取修正、响应相关检测部分|每个实际query|

第一版依赖标识采用目标版本和现有状态revision；相关部分在更新后标dirty，下一次使用前准备一次。不增加用户生命周期管理框架，不长期缓存每个query的结果。已有view的dirty刷新是Design 1已有机制，Design 3的新增点是让检测准备和view准备共享这次状态准备，并决定这些中间量怎样进入共同执行路径。

保留原始摘要，不能假设其全部坐标可在每次写入时直接线性投影：长度归一化、producer统计和mask会变化。先仅共享经过既有归一化得到的同一源编码；增量投影不是首版的必需机制。

### 3.2 精确拆分当前225维检测

对一个层/head，令当前选定坐标的Cholesky因子为

\[
G=H_{II}=LL^\top,\quad
L=\begin{bmatrix}L_{xx}&0\\L_{ox}&L_{oo}\end{bmatrix},\quad
f_I=\begin{bmatrix}x\\o\end{bmatrix},
\]

其中x为33维源编码，o为该层192维完整native响应经过**当前冻结**中心化和尺度变换后的坐标。

状态准备一次计算

\[
t=L_{xx}^{-1}x,\quad h=L_{ox}t,\quad d=\|t\|^2.
\]

当前query只计算

\[
v=L_{oo}^{-1}(o-h),\qquad \underline u_I^2=d+\|v\|^2.
\]

这是现有三角求解的分块展开；不需要谱近似、额外逆矩阵或重新拟合。逐层/head原本不同的因子保持不同；不能因x或o相同就把head统计混为一个。原长度、mask和最大值聚合保持，检测阈值及a、b保持。

设状态在失效前有q个query，用主阶乘加计数说明潜力：现路径约`q*(33+192)^2`；拆分约`33^2+2*192*33+q*192^2`，另计范数、相减、状态存储和调度。q=1时主阶算术相同，q>1才消除重复源部分。即使q很大，求解主阶的节省上限也仅约27.2%，不是数量级加速；单query若存取成本更高，应直接使用原求解而不物化状态中间量。

这是可独立验证的小优化，不把它单独当Design 3全部贡献。主要待验证收益还来自共享读出与执行组织。块求解虽然数学等价，浮点结果可能改变阈值附近判定；第一版保持FP64检测，对近阈值或数值异常请求回到原完整求解，并计入费用。数值容差只用于选择参考求解，不修改策略阈值。

## 4. 机制二：在读取的消费端完成修正和证据

一层的native读取得到完整响应r之后，Design 1需要`Tr+b+Aq`，Design 2需要其标准化响应o。两者共享同一份r和状态编码，按同一次读取执行：

1. 若状态dirty，先准备view和检测的源相关部分；未dirty则引用已有结果。
2. 正常attention读取产生r；当r完整可用时，完成响应转换、view修正和需要的检测。
3. 修正后输出继续进入上层；检测只累计原规则所需的最大值，不为生产服务保存完整层/query trace。
4. 最终分数和筛查结果就绪后进入Design 2原状态转移，不能在下层提前改变上层query路径。

实现候选是紧凑的读取后处理算子，或在合适的attention尾部融合；具体边界待资源测量选择。T跨head、检测依赖完整192维响应，不能声称每个head独立读取时即可完成一切，也不能在history分块尚未归约完时执行二次型。若全融合提高寄存器压力并拖慢主读取，就在完整r边界用一个独立后处理算子，仍共享输入布局和调度。

希望减少的是响应/标准化/拼接/修正等中间张量写回、重复参数装载、小算子launch及Python/设备同步。**当前算法已经只需一次native读取，不把“去掉第二次完整KV扫描”虚构为新增收益。** 性能对照需包含去掉诊断trace的简洁实现和通用编译基线，避免仅证明日志开销很大。

Armed状态需要筛查；Observing、Spent、Installed按原状态机跳过不再需要的筛查算子；Installed使用native路径。确定性layer-clearance可跳过贡献为零且没有其他消费者的修正计算，不能跳过仍被上层或检测使用的输入。提前按状态分派执行图，减少计算后再乘零的工作。数学语义相同的跳过仍须分别记录实际FLOPs变化。

## 5. 机制三：沿真实状态依赖安排轻重工作

同一执行器有两类就绪任务：正常读取/必要view准备，以及目标构建/目标推进。两类都引用相同的版本、状态revision和请求边界。

- 同用户保持事件先后、当前评分与随后写入的顺序；服务缓存和witness各自推进，不共享错误的上层状态。
- 在已有可并行请求之间按目标、模式、适当长度区间分组；使用已经就绪的请求，不要求积累16个同用户候选。分组不能通过无界等待换取吞吐。
- 目标构建采用依赖闭合的块，在合法块边界让出执行机会。额度准入先按原Design 2规则判断整个观察是否可做；执行器只切分已准入工作，不能因为排队或分块就丢弃原本应执行的观察。
- 先满足其他用户可就绪的正常读取，同时为已准入目标工作保留执行进度，防止纯优先队列饿死触发请求。首版只需简单有界交替，不研究通用最优调度器。
- witness已含可安装KV，接管优先转移所有权/引用，避免复制整份KV；摘要重建可在构建/追加中消费实际写出的KV。它只消除额外遍历，不能省略summary应包含的真实信息。

**重要边界：触发用户的当前响应必须等待目标构建和比较。** 不能先返回旧分数、把重建放到后台来声称延迟下降；该改变已经在Design 2对照中损失尾部保护。这里减少的是对其他用户的阻塞和无用复制，并尝试缩短必要构建本身。单GPU分块只在块边界可调度，并非任意kernel抢占；块太小也会增加launch和重读成本。

不为得到调度收益改变同一用户未来输入，也不引入模型并发发布的复杂协议。先在冻结模型、同步状态语义、固定到达序列下比较。吞吐提升导致的现实用户反馈变化属于后续线上问题，不能由离线重排证明。

## 6. 为什么三个机制是一个设计

三者围绕同一个问题：**一个状态在什么时刻需要哪些计算，已产生的结果能被哪些后续操作使用？**

机制一确定计算有效期，提供一次状态准备；机制二让这些结果在真正的读取消费端共同使用；机制三按同一状态依赖安排准备、观察和接管。目标不在于分别加上“缓存、融合、调度”三个常见词，而是形成一个从状态变化到计算失效、从读取结果到检测、从目标构建到状态接管的共同执行流程。

若测量发现某机制没有端到端价值，就删去它，保留更小的设计；不以满足三模块外观为目标。若最终优势仅来自通用编译、普通batching或删诊断日志，应承认专门执行贡献不足，而不能强行写成独立研究点。

## 7. 对应八项原则

|原则|具体落点|什么结果会否定这项优点|
|---|---|---|
|利用方法特有结构|冻结共享参数、状态源编码、真实响应、目标缓存接管共同组织|通用编译/相同batching已经获得全部收益|
|解决主要瓶颈|优先测state准备、read后处理、构建和同步占比，再决定融合边界|优化部分占比过低，端到端收益消失|
|减少实际工作|源相关求解去重、中间张量减少、合法零贡献跳过、接管避免整KV复制|额外物化、分派和存储抵消节省|
|少数统一机制|状态有效期→消费端执行→依赖有序调度|必须堆叠多个无关case补丁才能有效|
|保持算法语义|同C/H/坐标/阈值/额度，返回与安装顺序不变|收益依赖少做检查、延迟响应语义改变或错误状态共享|
|兼顾普通与干预|轻重任务分块交替，分别统计普通/触发请求延迟|普通p99因重建明显恶化，或目标任务饥饿|
|不依赖大batch等待|真实请求组优先，q=1直接路径，只组合已就绪独立工作|只在人工16/64候选或无限等待下加速|
|完整系统证据|准备/服务分账，最终合并，含搬运、同步和内存|微算子快而端到端慢，或Exact对照未获得同等通用优化|

## 8. 后续Benchmark草案（本轮不执行）

先固定比较问题，再做实现；以下是待采用的实验结构，不是已观察到的瓶颈或收益。

### 负载与对照

- 保留Design 1成熟域及Design 2的2048自然/2034富集真实轨迹，分别评价，不把人群混成有利平均值。
- 主负载按真实候选组、事件与请求比例运行；1/2/4/16候选仅作为共享次数敏感性，16不是主条件。
- 覆盖dirty频繁/稀少、普通请求/构建触发/继续观察/已安装native四种工作，及实际长度分布。
- 第一阶段测无排队执行耗时；调度阶段使用固定到达模型，说明负载强度。历史业务时间戳不自动代表GPU请求到达率，压缩时间轴需明确标为负载仿真，不是生产测量。
- 对照依次为现原型、移除诊断开销的简洁实现、相同布局和batch机会的通用编译实现、逐步增加上述机制；Reuse和Exact获得同等通用优化。

### 观察指标

端到端吞吐、普通/触发请求p50/p95/p99、排队与执行时间分解；视图刷新次数、状态准备命中数、kernel次数、实际可测内存流量和中间张量峰值；目标工作完成等待、候选驻留与额外KV峰值；全部实际FLOPs。prepare、service、evaluation teacher三者分账，生命周期再合并。不能用推算的HBM流量替代硬件实测而不说明。

校验分数偏差、筛查/安装动作、追加淘汰后KV轨迹、原算法额度准入、所有原质量指标。第一轮冻结Design 2的算法收费规则和额度以隔离执行收益，同时另记优化后实际算术；不得因为kernel改变FLOPs就悄悄增加观察次数。以后若按新成本重设额度，应作为新的策略实验。

### 阶段判断

1. 最小正确性检查：同一状态、一次写入前后、一个真实接管，核对准备失效、求解分块和状态轨迹。
2. 性能分解：先找到实际瓶颈，按占比估算可达上限，决定是否值得融合/调度。
3. 中等规模完整回放：在主真实负载上有端到端净收益，普通尾延迟没有因干预而大幅恶化，质量与动作保持。
4. 只有上述成立，才将执行机制加入论文主贡献。加速目标的数值应在第一轮基线测量后、候选优化前固定；本纸面阶段不虚构2倍或5倍目标。

不在本轮实现kernel、调度器或跑实验；不替换现有论文主方法，不改变Design 1/2冻结参数。
