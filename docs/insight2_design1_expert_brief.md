# EvoKV：从跨版本状态不兼容到 Sketch-to-Sketch State Migration

更新日期：2026-09-05

本文是当前 Design 1 的论文设计稿，按 Motivation、Insights 和方法流水线组织。第 3 节说明各组件
的作用、输入输出及连接方式；具体技术约定与评价协议见
[experimental_design.md](experimental_design.md)，已有观察见
[motivation_observations.md](motivation_observations.md)。当前方法处于设计阶段，尚无方法实验结果。

## 1. Motivation：让模型更新的收益在持久化状态上兑现

持久化推荐系统将用户历史保存为逐事件 K/V，并在后续请求中反复读取。模型发布时，推荐模型的
参数已经更新，用户缓存却仍由 Parent 模型生成。已有观察表明，即使 Current 模型在完整重算
历史时取得更好的推荐质量，直接读取 Parent K/V 仍会损失一部分更新收益。

这使模型发布包含两个相互关联的任务：训练更好的模型，以及让已经保存的用户状态适应新模型。
EvoKV 关注后一个任务。它在 Current 通过 Full-only admission 之后工作，目标是在受限的计算
和 I/O 预算下，使大量用户尽快受益于新的推荐模型。

全量重算可以为每个用户生成 Current K/V，但需要集中读取历史、运行模型并写回完整状态。
对于持续积累历史、反复消费用户缓存的推荐系统，这些工作会成为发布成本和完成时间的重要来源。
EvoKV 因此研究如何保留已有缓存，通过较小的状态转换改善 Current 对旧历史的读取。

## 2. Insights：把迁移目标放在历史被读取的地方

### 2.1 Insight 1：局部重算难以覆盖分散的版本差异

已有诊断发现，跨版本差异分散在多个历史位置和多层状态中。替换少量 token、单层或单侧 K/V，
通常只能恢复部分差距；取得较高恢复率需要覆盖更大范围。实际重算还要处理这些状态的上游依赖，
因而不能只按被替换条目的数量估算执行成本。

这一观察促使我们保留普通 K/V 所提供的完整历史信息，寻找一个能够以较小状态表达版本变化的
迁移接口。

### 2.2 Insight 2：历史聚合提供了紧凑的修正位置

历史 K/V 通过当前请求的 query 参与键匹配与值聚合，随后影响推荐输出。已有 HSTU 诊断发现，
虽然差异分散在底层状态中，它们对预测的主要影响可以在历史聚合处用较紧凑的响应修正表达。
这一结果为迁移提供了一个直接的切入点：修正 Current 读到的历史响应。
[对应的 discovery 报告](../results/yambda500m_medium_seed17/insight2_functional_boundary_v1/discovery_functional_boundary/analysis_v2/report.md)。

服务中的 query 和存活历史会不断变化，因此系统需要一种能够持续读取和更新的修正状态。
EvoKV 选择以短摘要承载这种状态：在普通缓存写入时生成摘要，在发布时学习摘要的版本转换，
再由当前 query 将摘要变化转化为本次请求所需的响应差。

两个 Insights 在设计中分别对应“保留普通 K/V”和“在历史聚合处注入修正”。Migration Sketch
连接这两个选择：它提供发布时可快速处理的用户状态，使共享的版本转换能够用于每个用户。
方法的效果由后续推荐质量、持续更新表现和系统成本共同评价；已有诊断作为设计依据保留。

## 3. Design 1：Sketch-to-Sketch State Migration

### 3.1 Overview：从摘要写入到版本修正

EvoKV 在普通 KV cache 之外，为每个用户维护一份 Migration Sketch。模型生成事件 K/V 时同步
写入摘要；新模型定版后，共享的 Sketch Translator 将已有摘要转换为面向新模型的摘要；
请求到达时，Paired Reader 将新旧摘要的响应差加入普通 K/V 的历史聚合。

普通 K/V、Source Sketch 和 Current Sketch 在这条路径中分别承担基础历史、翻译输入和读取
修正的职责。Source 始终对应实际生成这些 K/V 的模型，Current Sketch 则随服务目标版本更新。
系统由此形成面向 Current 的逻辑缓存视图，正式发布只处理短摘要，无需物化和写回完整
Current K/V。

~~~text
事件写入：事件前向 → 普通 K/V + 带 producer 标记的 Source Sketch
                                  │
模型发布：独立用户校准 Translator → 翻译 Source → Current Sketch
                                  │
请求读取：普通 K/V 响应 + Current 摘要响应 − Source 摘要响应
                                  │
                           原模型后续计算

持续更新：追加、淘汰 → 维护 Source 与翻译结果
再次发布：各 producer 的 Source → 面向新目标版本的摘要
~~~

本设计包含四项相互连接的机制：版本化摘要定义系统保存什么状态，Sketch Translation 定义
如何学习并执行版本转换，Paired Reader 定义修正怎样进入模型，持续状态管理定义这些操作如何
跨事件和模型发布反复执行。下文先说明一次发布的基本流程，再说明多个来源版本共存时的处理。

资源也沿这些路径计量：摘要写入分摊到正常服务，校准和全人口翻译计入发布工作，请求读取与
历史更新承担持续开销。一次性发布计算以相同人口 Exact-All 的 20% 为设计预算，持续服务成本
在相同运行时段内另行比较。

### 3.2 Migration Sketch：版本化的历史摘要

Migration Sketch 为发布准备可快速处理的用户状态。用户事件按时间顺序进入固定容量的
segment，每段在每层维护少量 summary slots。每个 slot 汇总固定事件区间，保存 K/V 累加量、
事件数量、时间和位置统计；读取与翻译时由累加量形成平均 K/V。

参考配置中，每段最多包含 64 个事件，两个 slots 分别汇总前后各 32 个位置。边界对齐的
1,024-event 历史对应 16 段、每层 32 个 slots。在线窗口两端及发布时未满段的额外容量一并
预留。slot 数量决定摘要的表达能力及存储规模，segment 容量决定版本管理和淘汰的粒度。

事件在写入时确定所属 slot，并在存活期间保持这个归属。writer 复用模型已经生成的 K/V，
向对应累加量加入事件贡献，同时记录数量和时间位置统计；移除事件时从相同统计中扣除。
读取结果按 slot 代表的事件数量加权，空 slot 通过有效性标记排除。

每个 segment 保存实际 producer version。模型切换时封存尚未写满的旧 segment，新模型从
新段开始写入。即使用户的历史跨越多次发布，每段的 Source Sketch 仍与产生该段普通 K/V 的
版本对应。翻译结果另存为面向当前服务模型的视图，保留自己的目标版本与 source revision。

同一 release family 固定层/head 接口、segment 规则、slot 划分和字段格式，使成对摘要中的
对应位置描述同一组事件。版本改变时转换 K/V 载荷，事件数量、有效性及时间位置由状态维护
路径保留。这个约定也让同一 reader 能对新旧摘要进行对应读取。

摘要维护只增加聚合和持久化更新。存储计入 Source 累加量、翻译载荷、统计字段和边界容量，
并按实际精度核算。对于尚未保存 Source Sketch 的已有缓存，首次接入从旧 K/V 构造摘要；
完成初始化后，后续发布直接读取已经维护的短状态。

### 3.3 Sketch Translation：共享校准与发布迁移

Sketch Translation 将学习版本变化和应用版本变化连接为同一条迁移路径。每个目标版本使用
一个共享 Translator：在固定校准人口上学习转换，再将它应用到全量用户的 Source Sketch。
先考虑 Source 均由 Parent 产生的一次更新，参考设计采用残差输出：

\[
\widehat S_u^c=S_u^p+T_{p\rightarrow c}(S_u^p).
\tag{1}
\]

式中的摘要表示 K/V 载荷；结构信息随摘要携带。Translator 读取同用户需要迁移的各段、各层
Source，先编码为短序列，再结合段间上下文输出对应位置的 K/V 残差。跨段输入使某一段的
转换能够参考前序历史摘要。网络容量在开发阶段确定，所有用户共享这组参数。

Current 完成正常训练和 Full-only admission 后，系统冻结模型参数，只校准 Translator。
校准用户预先划分，并与开发和正式评价用户分离。对于相同的可见历史前缀，Parent 与 Current
分别生成完整 K/V，再按统一规则构造摘要，形成转换所需的监督。

训练结合摘要重建和响应差两个目标。摘要重建使预测载荷接近真实 Current Sketch；响应差目标
使两份摘要的读数之差接近 Current 读取两版完整历史时的响应变化。参考训练使用固定尺度的
载荷均方误差与响应均方误差的加权组合，前者约束输出表示，后者对齐实际注入的修正。

响应监督使用同一个 Current query 读取两版完整状态和两份摘要。校准按部署路径逐层生成
query：下层完成修正后再进入上层。查询前缀只包含此前可见的事件，并覆盖真实事件追加与
部分淘汰后的摘要形态。

Current 与 Translator 定版后，发布任务批量读取 Source Sketch、生成 Current Sketch，并
保存目标模型、摘要格式和 source revision。请求按这组标记取得匹配的模型与迁移状态。
Source 在翻译期间发生变化时，任务刷新结果；Current 已准入但摘要尚未就绪的用户按 Reuse
路径服务，随后切换到 paired read。覆盖人口、完成时间和过渡期请求一同计入发布评价。

完整 Current K/V 的教师计算集中在校准集，全量用户只执行摘要翻译。校准人口控制离线学习
成本与泛化覆盖，Translator 容量控制转换能力及单用户处理成本；这些工作与必要的摘要初始化
共同计入发布预算。

### 3.4 Paired Reader：查询驱动的历史响应修正

Paired Reader 将发布时生成的摘要视图用于实际推荐请求。在每层，Current 先使用当前 query
读取普通缓存，得到基础历史聚合；再用同一个 query 读取新旧两份摘要，将响应差加入基础结果：

\[
\widetilde A_c(q)
=
A_c^{\mathrm{base}}(q)
+
R_c(q,\widehat S_u^c)
-
R_c(q,S_u^p).
\tag{2}
\]

这里 base 是本次执行对实际缓存的读取，R 表示摘要读取。单次更新时，两份摘要覆盖需要迁移的
Parent 历史；存在多个旧 producer 时，对这些旧段分别读取并合并响应差。目标版本新写入的
segments 直接通过普通 K/V 路径参与聚合。

三个读数各有分工。普通 K/V 提供完整历史的基础响应，Source Sketch 提供旧状态在摘要尺度
上的参照，Current Sketch 提供翻译后的参照。作差将附加路径集中于版本变化，避免把整份
Current 摘要的响应重复加入历史。新旧摘要采用相同的事件划分与读取规则，使比较对应相同区间。

在 HSTU 中，摘要读取沿用 Current 的 query-key 匹配、激活和值聚合，并按 slot 的事件数量
加权。位置和时间由摘要统计给出，使用原模型的偏置和缩放规则。所有历史响应差在聚合后
归一化之前合并，再与模型规定的暂态贡献一起进入原有归一化、门控、输出投影和残差计算。
[HSTU 原论文，第 3 节](https://arxiv.org/html/2402.17152v3#S3)。

当前层完成后，模型继续生成下一层 query。修正因此直接参与后续计算，也可用于真实新事件
生成 K/V 时的历史读取。候选评分产生的暂态状态只参与该次请求，不写入持久化摘要。

query 与摘要 key 的匹配使一份翻译结果能用于不同候选和请求。同维度下，两份 32-slot 摘要
相对 1,024-event 历史增加约 6.25% 的对应 QK 与值聚合算术工作；实际延迟和吞吐由实现测量。
随旧 segments 淘汰，需要 paired read 的摘要数量减少。其他 attention 结构需按其归一化
方式适配这一读取接口。

### 3.5 State Evolution：历史更新与连续模型发布

状态管理负责在事件变化和模型再次发布时，维持普通 K/V、Source 和目标摘要之间的对应关系。
每段长期保留 producer 与 Source，稳态只保存一份面向当前目标版本的翻译视图。这个组织方式
使同一套读写路径可以跨发布重复使用。

**日常追加与淘汰。** Current 用 paired read 读取已有历史，完成新事件前向，将 K/V 和
Source 写入当前版本的 segment。多个事件按时间顺序推进，每个事件只读取此前可见的历史。
淘汰先扣除 slot 中的事件贡献，再移除普通 K/V；整个 segment 退出时，其摘要与版本信息一起
移除。Source 改变后，系统刷新该用户剩余旧段的翻译结果。参考 Translator 使用跨段输入，
因此刷新覆盖这些输出，并将新 Source 与目标视图按统一修订提交。

**从一次更新扩展到连续发布。** 假设 V0 更新到 V1 后，一部分 V0 历史尚未淘汰，V2 已经
准入。该用户此时同时持有 V0 和 V1 生成的 K/V。V2 的迁移任务读取这些段各自的原始 Source，
统一生成面向 V2 的摘要；此前面向 V1 的翻译结果在新视图就绪后被替换。新事件随后进入
V2 segment，旧段继续由原 producer 标记识别。

为处理这种混合来源，每个新目标版本的 Translator 接收需要迁移的 Source 序列及各段的
producer 标记，结合跨段上下文预测同结构输出。Source 版本作为条件输入区分不同表示来源，
覆盖范围由当前仍被服务的缓存版本确定。系统始终从原始 Source 转换到目标版本，避免把
上一轮预测摘要继续作为下一轮翻译输入。

多来源校准沿预先确定的发布与事件顺序构造输入，保留此前版本在实际迁移、追加路径上产生的
Source，再生成最新目标模型的教师摘要与响应。这样，校准覆盖混合版本及其生成上下文。
单次更新中独立构造的 Parent/Current Full 配对是这一流程的基础情形；多个相邻更新各自成功，
仍需通过实际连续轨迹评价整条流程。

**发布重叠与视图切换。** 请求绑定一个目标模型版本及匹配的摘要修订。新版本准入后，迁移
任务以新目标翻译 Source；过期目标的迟到结果不再提交。尚未取得新目标视图的用户按该目标的
Reuse 路径服务，取得匹配结果后整体切换。旧视图在已有请求释放引用后回收，构造新视图所需的
临时缓冲计入峰值存储。被拒绝的模型候选保持当前服务目标与状态谱系。

**版本覆盖与退出。** 低活跃用户可能长期保留较早版本的历史。新 Translator 的校准与版本
支持需要包含仍有存活缓存引用的来源；对未覆盖来源的用户，系统显式采用 Reuse，并计入迁移
覆盖与整体质量。来源版本退出支持集合以相关缓存和在途任务不再引用为条件，旧目标 Translator
则在其服务请求及迁移任务结束后退出在线使用。

持续评价按完整发布序列累计校准、翻译、请求读取和刷新成本，并观察迁移历史上新生成 K/V 的
质量变化。连续发布沿用上述四个组件，新增的关键管理对象是来源版本、目标版本和视图修订。
这一机制属于论文设计范围；现有单边观察与执行合同仍保持各自范围，连续版本效果需单独评价。
