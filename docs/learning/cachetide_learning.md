## U1 第 1 步 从用户历史和候选到分数

本步的中心问题：用户过去做了什么，与系统现在准备推荐什么，怎样共同决定分数？先看一个小例子。

### 1 场景与任务

在当前请求发生前，用户按时间顺序做了三件事：

| 历史事件 | item | 行为 | 相对时间 |
| --- | --- | --- | --- |
| e1 | 跑鞋测评视频 | 完整观看 | 昨天 |
| e2 | 马拉松训练视频 | 点赞 | 今天早些时候 |
| e3 | 相机评测视频 | 很快划走 | 刚才 |

现在要比较两个候选：跑步教程和相机广告。这里的“候选”，就是系统正在考虑要不要推荐给用户的内容。系统给它们各算一个分数，用于这个例子中的排序。候选尚未成为已经发生的用户行为；此刻还不知道用户会不会点击、点赞或划走。

本步只用中文名称：用户历史、当前候选、模型和候选分数。模型结合已知信息，分别评价这两个候选；具体怎么结合，就是下面两条路线的区别。

你在本步需要掌握的是输入、依赖和输出。分数的具体任务含义需要结合训练目标和评分头确认；仅凭一个数值不能说它是点击概率。

### 2 五种容易混淆的对象

| 对象 | 是什么 | 在例子中的含义 |
| --- | --- | --- |
| item ID | 区分内容或商品的标识 | 跑鞋视频的编号 |
| 历史事件 event | 已发生的一次交互记录 | 某时刻对跑鞋视频完整观看 |
| embedding 嵌入向量 | 将 ID 或特征映射得到的数值向量 | 表示某 item 或某种行为的向量 |
| hidden representation 隐藏表示 | 网络加工后的中间向量 | 结合前序事件后，对该事件或用户状态的表示 |
| score 分数 | 评分过程的输出 | 当前候选 A 的一个排序分数 |

把 ID 想成“索引”，把 embedding 想成“模型用来计算的表示”，会更容易区分它们。编号 100 和编号 101 相邻，不意味着这两个 item 更相似；embedding 的各个坐标也不一定能直接解释成“运动兴趣”“相机兴趣”。

一个事件可能包含 item ID、行为、时间以及其他当时已知的特征。它不是单独一个 item：同一个视频的“点赞”和“划走”是不同的交互记录。

隐藏表示又不同于输入 embedding。若某个位置的表示结合了前面的历史，那么即使这个位置的 item 相同，前序历史不同也可能得到不同表示。

这里说的是可能存在的依赖关系。当前工程具体用了哪些事件字段、如何融合 embedding、在哪些位置加入时间信息，留到对应的代码小节核查。

### 3 路线一 先概括用户再比较候选

想象你要帮朋友选视频。你先看完他的观看记录，形成一份概括：“最近比较关注跑步，也曾很快划走一条相机视频。”形成这份概括时，你还没有考虑这次具体要推荐哪个视频。

然后拿同一份概括，分别判断：

- 跑步教程：和这份用户概括是否匹配？据此给它一个分数。
- 相机广告：和这份用户概括是否匹配？据此给它另一个分数。

计算顺序是：

```text
用户历史 → 形成一份用户概括

同一份用户概括 + 跑步教程 → 跑步教程的分数
同一份用户概括 + 相机广告 → 相机广告的分数
```

这份“用户概括”，就是原来所说的“用户表示”。真实模型通常用一组数字表达它；这里用一句话帮助理解它在计算流程中的作用。它可以表达多种兴趣，不一定只有“喜欢跑步”一个标签。

“候选无关”的含义很具体：**形成用户概括的这一步，不需要知道当前要评价哪个候选。** 因此，在历史和模型等条件不变时，换一个候选仍可以使用同一份用户概括。

候选随后参与匹配，所以两个候选仍然可以有不同分数。需要区分“共用用户概括”和“得到相同分数”。

### 4 路线二 根据当前候选有侧重地读历史

仍然是那位朋友、同样三条记录。这次，你带着具体问题查看历史：“这个人会不会对跑步教程感兴趣？”

面对跑步教程，你可能更重视：看完跑鞋测评、点赞马拉松训练。这些记录与当前要判断的内容更相关。

接着换一个问题：“这个人会不会对相机广告感兴趣？”你可能更重视：他曾很快划走相机评测。相关记录也可能提供负面线索；相关不等于喜欢，而且一次划走并不能证明他讨厌所有相机内容。

计算顺序是：

```text
用户历史 + 跑步教程
    → 根据跑步教程，组织和利用历史信息
    → 得到针对跑步教程的判断依据
    → 给跑步教程打分

同一份用户历史 + 相机广告
    → 根据相机广告，组织和利用历史信息
    → 得到针对相机广告的判断依据
    → 给相机广告打分
```

原来的“候选参与历史读取”，意思就是：**当前要推荐什么，会参与决定怎样利用用户过去的记录。** “读取”不只是从磁盘打开文件，这里还包含模型怎样结合、加工这些历史信息。

可以先把它理解为“带着不同的问题看同一份经历”。历史本身没有被改写，但为当前候选形成的判断依据可能不同。

这不要求只保留相关记录，也不要求一定重新计算全部历史。为了便于理解，我们假设模型先把每条历史整理成可读取的表示；这部分若不依赖候选，就可以供两个候选共用。随后根据候选利用这些表示，才形成各自的判断依据。

### 4 补充 两条路线到底差在哪里

两条路线都使用用户历史，也都考虑候选，最后都给候选打分。要看的是候选参与的时机：

| 比较点 | 路线一 | 路线二 |
| --- | --- | --- |
| 先做什么？ | 从历史形成一份固定的用户概括 | 可以先整理历史，再结合当前候选读取 |
| 候选参与什么？ | 和已有的用户概括进行匹配 | 参与形成针对自己的历史判断依据，再评分 |
| 换候选后，中间判断依据怎样？ | 继续用同一份用户概括 | 利用历史的侧重点与形成的依据可能改变 |
| 本例能共享什么？ | 形成好的用户概括 | 不依赖候选的历史整理结果 |

复习时记住两句话：

- 路线一：**先概括这个人，再看哪件内容适合他。**
- 路线二：**先知道要评价哪件内容，再结合他的经历形成判断依据。**

这是教学用的两种简化结构。不能由这个例子断言路线二一定更准确，也不能断言当前仓库就是其中某个完整结构。

### 5 用维度检查自己有没有理解

这小节可以在第 3–4 小节理解后再读。暂时假设每个历史事件用一行数字表示，每行四个数；一共有三条历史、两个候选。“维度”在这里就是一个向量有几个数。

| 量 | shape | 每一维表示什么 |
| --- | --- | --- |
| 历史输入向量 | `3 × 4` | 三个事件，每个四维表示 |
| 整理后的历史表示 | `3 × 4` | 三个经过加工的位置表示 |
| 候选向量 | `2 × 4` | 两个候选，每个四维表示 |
| 路线一的用户概括 | `4` | 一个候选无关向量 |
| 路线二的读取结果 | `2 × 4` | 每个候选各有一个四维读取结果 |
| 分数 | `2` | 每个候选一个分数 |

现在只需要看懂：三个历史事件各自可以有表示；路线一还形成一个共享的用户概括；路线二则可以为两个候选分别形成一个读取结果。它们最后都输出两个分数。具体怎样用数字算分，放到单独的小步学习。

这张表省略 batch、多个 head、多层和多任务输出，目的是理解“哪一个维度对应历史，哪一个对应候选”。它也没有规定一个真实事件只能编码成一个 token；实际 token 化方式需要单独核对。

### 6 召回与排序究竟在问什么

召回 retrieval 通常从很大的 item 集合中找出值得进一步考虑的候选；排序 ranking 则对已有候选计算与目标行为有关的分数。两者可以使用不同结构和目标，不能只按有没有 dot product 来辨认。

HSTU 原论文 §2.2 给出具体的两类序列任务：retrieval 预测与后续正反馈内容有关的 item；ranking 将已知候选内容作为条件预测用户动作，采用候选参与交互的表述。以上两张计算图是帮助理解依赖的简化例子，不是论文或当前代码的完整结构。[原论文 §2.2](https://arxiv.org/html/2402.17152v3)

读原文时，先问“输出是内容身份，还是对已知内容的用户行为预测？”，再问“候选在哪一步进入计算？”。这样比把所有推荐任务都当成“用一个用户向量做点积”更准确。

两种路线也不构成质量排名：候选较晚进入计算可能方便复用；候选参与历史交互提供了不同的表达方式。具体质量、成本和适用场景需要对应的证据。

### 7 当前请求和训练更新要分开

在本步的推理例子中，模型参数固定，模型根据输入计算分数；没有根据这次请求尚未发生的点击或划走更新参数。模型参数可以先理解为训练得到的、用于计算的数值设置。

训练则利用允许使用的数据与目标计算损失，并通过优化过程更新参数。候选当前的未来反馈不能放入当前请求的历史输入。已经发生的旧反馈能否使用，也取决于具体训练或校准协议，而不是“有这个字段就能用”。

更换候选、追加一个已发生事件、更换模型版本，是三种不同的变化：

| 改变 | 教学例子中哪些依赖可能改变？ |
| --- | --- |
| 历史与模型固定，更换候选 | 候选表示、候选相关读取和分数可能改变；候选无关的历史编码可共享 |
| 模型固定，历史追加事件 | 历史改变；哪些旧中间量能复用要看计算是否具有相应因果与增量性质 |
| 历史固定，模型换成新版本 | 历史编码也可能改变，不能因为原始历史相同就断言旧中间量有效 |

这三种变化会在后面的缓存小节分别分析。本步先记住：**判断能否复用一个量，要看它依赖的输入、参数及执行条件是否仍然满足要求。**

### 8 本步需要掌握的全部内容

完成本步，你应能独立做到：

1. 区分 item ID、已发生事件、输入 embedding、隐藏表示和输出 score。
2. 解释历史事件与当前候选的身份不同，当前候选的未来反馈不能作为已知输入。
3. 画出“先得到用户表示再匹配”与“候选参与历史读取”的两种计算图。
4. 根据计算步骤需要哪些信息，判断中间结果是否依赖候选。
5. 解释共享历史表示为什么仍可产生不同的候选读取结果。
6. 看懂简化例子中的历史条数、候选数量与每个向量的数字个数；具体向量运算后续单独学习。
7. 区分召回与排序、固定参数的请求前向计算与训练更新。
8. 解释为什么“历史相同”不足以证明跨模型版本的中间量相同。

本步到这里结束。HSTU 层公式、Q/K/V、mask、rank8 编码与 CUDA 执行在后续步骤讲解。

### 10 自查问题

这些问题用于发现卡点，答案在下一小节。可以先自己尝试；是否查看答案不会自动改变进度记录。

- Q1：同一个 item 昨天被完整观看、今天被很快划走，是同一个 item 吗？是同一个事件吗？它们的隐藏表示必然一样吗？
- Q2：历史先整理好，然后分别根据跑步教程和相机广告读取。在历史与模型不变时，哪部分可以共享？哪部分可能随候选变化？
- Q3：如果连整理历史的过程都考虑了当前候选，还能仅凭原始历史相同就断言整理结果相同吗？
