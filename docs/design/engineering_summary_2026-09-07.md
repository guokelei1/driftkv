## 当前实现到了哪里

四组件已经接入同一个六层执行器，并经历实际追加、部分及整段淘汰、多个producer长期共存、
五次模型发布和继承误差。模型仍为冻结的M0–M5；未新增backbone训练。C0–C5表示实际服务
状态，不能把整个C_i缓存标成由M_i生成。历史文件中的v编号保留以维持证据引用。

最后的方法版本是方案15：同原实际source均值、producer占比和发布后写入年龄，预测每层每head
的b＋Q A。query坐标的共享归一化折回发布系数；校准逐层推进，已拟合的下层固定后，再收集
下一层的实际query。每层一个rank32源映射，比原跨层共享rank32映射更大。
每用户query矩阵有36864个FP32值，即147456 bytes，另有常量、source、writer与metadata。
这个矩阵大小不能被“rank32”一词掩盖；最后一个静态用户快照也不是人口峰值存储。

## 实践中最有价值的工程改动

**将真实写入和候选读取分开。** 方案3采用原生写入、CC查询修正，既避免将不匹配的校准修正
写入未来K/V，也允许写入后只标dirty，在下一次CC前刷新。该改变有模型误差诊断依据，
不是为了省计算而忽略状态变化。

**复用原生滚动算子，批量重放同一计算。** 原逐事件执行变为按真实请求边界处理事件chunk，
仍先淘汰再追加，不跨用户注意力，不把未来事件放进前缀。保留了逐请求及K/V参考比较；
这使完整五段和6000用户评价成为可负担的开发任务。

**按实际长度分组，复用确实不依赖参数的状态。** 原生写入状态可以在校准pass之间复用，
但修正后的query和教师响应仍要重算。Teacher/Parent相同前缀在一次校准中复用，未被loss使用
的teacher logits不再额外计算。批量writer特征与view安装减少了逐用户的小算子调用。

**把源状态失效和查询变化分开。** 时间变化只改变已发布系数的读取权重，不必重翻译；
真实source变化仍触发dirty刷新。逐层依赖消退后可以关闭对应修正；writer继续服务下一发布。
这是语义允许的省计算，不能推广成历史变化后任意复用过期view。

**以原始请求合并结果。** 6000人评价分为12块，每块500 UID。每个用户完整经历五次更新，
统一合并请求再计算AUC；元数据和两基线要匹配。执行并行只改变资源调度，不改变用户、
请求、训练seed或缓存产生顺序。

## 出现过的问题与已采取的处理

| 问题 | 为什么会影响结论 | 当前处理 |
| --- | --- | --- |
| 初稿把冻结模型当作SiLU式HSTU | 会用错读取激活、缩放和归一化 | 以checkpoint配置确认legacy ELU+1、无序列分母、SiLU gate、inclusive self；正文通用叙述与实现边界分开 |
| 初期局部刷新只看少翻译了多少段 | 可能忽略质量下降和发射开销 | 转换段数18214→1837仍有明显实际写入开销；同时保留质量和墙钟 |
| CC修正用于write token | 当次误差可进入未来缓存 | 用真实write-token诊断定位，当前保留原生写入 |
| 旧producer淘汰后被误认为没有误差 | Current后代仍可能继承旧上下文 | 全历史响应目标、真实lifetime校准与结构消退；不以producer计数判定Exact |
| 原32/128/512用户结果被过度解读 | 用户分布、反馈量及负例集中度不足 | 固定6000开发与6000确认，确认输出未读；小探针仅作机制和资源检查 |
| 早期内存只计writer和translated view | 漏计materialized source view | 旧原始summary不改，汇总显式补计；方案12早期平方矩漏计也有单独修订记录 |
| 评估引用冻结译者后把准备成本看成零 | 教师、拟合和谱系生成仍是方法所需 | 各质量报告引用原校准完整账本；查询选择与候选选择也计入 |
| 旧保守公式与加速后的时间脱节 | 小校准被估为超过30分钟，影响调度 | 保留中止的资源探针，用已有测量解释估计并按规则启动；未把资源中止当质量失败 |
| 数值等价的编译路径存在输出别名和形状问题 | 可能让已发布view被后续图调用覆盖 | 候选分桶、输入连续存储、输出拷贝和逐请求参考检查；不把编译后速度用于未编译方案 |
| “五个目标”被误读为“五段完整服务” | 末段tail为0时没有M5真实服务 | 方案15首canary保留原样，另补14天末段检查；不称前者为完整五段质量 |
| M2低增益边占据优化重点 | 小或反号gap不能用恢复比例判断方法 | 用户指定M2 native No-op，仍经过M2真实模型与写入；旧负结果单列保留 |

## 本轮停止前的具体状态

原五边适配运行v15_query_view_quality6000_01因用户改变研究范围而停止，exit143。
三个已完成分块与中间证据保存在原目录，[interruption.json](../../results/design/v15_query_view_quality6000_01/interruption.json)
明确标记它不是完整6000人结果。没有删除不利请求，也没有将部分分块拼成完整评价。

针对query坐标折叠、count权重、视图清除、跨No-op后的producer谱系和原有状态逻辑，
最近相关12项检查通过。真实4用户五阶段canary共244请求：M2的63条输出逐元素等于Reuse，
其他四目标181条请求的所有列与原canary逐元素相同，实际追加、淘汰与发布计数一致。
证据见[四边canary检查](../../results/design/analysis/v15_four_edge_canary_checks.json)。

四个适配目标为M1/M3/M4/M5。M2作为原生边界记录仍出现在完整轨迹中。

最终运行状态为development_complete，父进程和12个分块exit均为0，耗时893.09s，
峰值GPU allocated为18324MiB。五阶段记录136610请求、4305名反馈用户；其中四个适配
目标为111228请求、4173名反馈用户。M2的25382请求全部逐元素等于Reuse且无活动修正。

[最终质量报告](../../results/design/analysis/v15_query_view_four_edge_quality6000_01_quality.md)。

边的配对方法差值区间均含0。原始请求和报告中仍保留M2 No-op行。

## 成本数字应该如何解释

早期局部变体把转换段数减少约90%，却没有按相同比例减少实际开销；Python控制、张量发射、
source打包和每次CC前刷新都可能主导小矩阵计算。应区分这些成本与attention算术量。

[方案9发布探针](../../results/design/v9_stratified_publication_01/summary.json)使用32个驻留真实状态
测得发布及backfill，再按30000人口实际历史长度外推Exact计算。五次发布的准备22.20s、
翻译约6.90s、初次backfill代理约4.81s，对Exact约204.30s，得到16.60%。
这不是30000人的实际I/O、峰值存储、迁移等待或完整服务测量。

已有6000人eager服务中，方案9稳定/时间条件化以及方案12/14的方法服务比率约为
1.055/1.058/1.095/1.076，且未包含全局准备和初始backfill。比率的分子、分母都包含
各自普通写入和读取，因此它既不是“适配额外成本占Exact重建成本”的直接比例，也不能
用来声称达到了发布20%目标。必须同时给出分项和固定服务区间的总账。

完整成本仍缺人口存储/I/O、真实就绪延迟及等待期写入后的后续影响。当前没有为这些缺口
补造估计或称其已完成。质量较弱的变体也没有仅靠执行提速被升级为有效方法。

最后方案15五阶段账本中，方法写入595.03s、读取355.17s、发布2.11s，合计952.31s；
Exact相应为545.67s、267.60s、106.92s，合计920.19s，比率1.0349。
另外还需原校准准备21.55s和初始摘要3.09s。跨GPU账本是各调用耗时之和，不等于总运行
墙钟893.09s。本轮方法M2为No-op，而Exact仍保留完整五阶段参考，因此该比率仅描述
实际执行，不能解释为四次迁移的同口径成本资格或将其变化归因于query view提速。

主执行器现有多个探索分支，应围绕选定表示做局部整理；没有必要先做通用框架、全测试覆盖、
持久化协议或生产并发系统。统计和公式变化用针对性参考检查，文本修改只检查内容与链接。

最后的CPU bootstrap汇总还暴露出一个执行问题：小向量计算启动大量BLAS线程，三个并行
报告进程各有约80个线程，分析耗时达到数分钟。它没有改变已核对的计算公式或抽样次数；
未来独立汇总时应限制BLAS线程并按实际耗时调度，避免将CPU过度并行误当作模型实验耗时。
本轮已让三个报告正常结束，没有重采样、减少重复次数或重跑模型。

本轮未重训backbone、未读取确认输出、未扩展四层/十层或theta3/RecFlow，也未修改或编译
论文。已有不利证据、历史封存和用户工作树修改保留。所有模型实验已经结束，后续方向留待
用户决定是否另开探索，不因旧合同、脚本或本总结中的建议自动恢复执行。
