## 阶段一：建立问题与 Motivation

固定 Medium、Large、Max 的 V0–V5 模型，完成 15 条相邻发布边的 Full/Reuse 对照。
随后测试层重算、尾部重算、偏差引导重算、query 引导重算，以及 Q、Q＋history 校正。
Q/H 经多轮输入、非线性拟合与成本配置调整，形成当前 Motivation 的结果和结构图。

**留下的观察：** 重用旧缓存会损失模型更新收益；局部重算的强恢复需要较多计算；
利用用户历史的读时校正有潜力，但历史编码成本需要解决。Q/H 是方向依据，不限定 Design 的结构。

## 阶段二：紧凑摘要原型（旧 Design 1，第 1–5 轮）

- **第 1 轮：** 用 K/V 分组统计生成用户摘要，拟合共享读取映射，建立万人匹配参照。
- **第 2 轮：** 缩小 PCA 摘要维度，并加入增长型混合状态校准。
- **第 3 轮：** 改成真实追加、淘汰的滚动校准，比较组内均值与贡献量摘要。
- **第 4 轮：** 加强个性化部分的正则，检查是否因拟合覆盖不足而过拟合。
- **第 5 轮：** 移除摘要或历史响应输入做消融，并检查用户抽样不确定性。

当时较好点恢复约 **59.45%**。已有低成本恢复，但摘要相对共享映射的增量不明确。

## 阶段三：第一次方向纠偏，开放方法选择（第 6–17 轮）

明确目标是读时校正达到至少 80% 恢复，而不是必须沿用某一种摘要或 Motivation 的 H。

- **第 6 轮：** 比较非线性 query 响应校正与逐条 K/V 读取视图；后者较好。
- **第 7 轮：** 联合拟合最终教师打分，并比较校正全部条目或仅旧版本条目；均未改善。
- **第 8 轮：** 在真实滚动状态中校准，加入条目生产版本及写入时上下文；未改善。
- **第 9 轮：** 检验完整维度仿射 K/V 映射与直接 K/V 监督；未改善。
- **第 10 轮：** 分别增加网络容量和校准 query 数；未改善。
- **第 11 轮：** 加入 Current 的物品 embedding，恢复提高到约 **77.63%**，成为有效输入。
- **第 12 轮：** 比较读取目标精炼与最终打分联合精炼，较好点约 **78.95%**。
- **第 13 轮：** 延长联合训练；未改善。
- **第 14 轮：** 交替纯旧状态与真实混合状态训练；未改善。
- **第 15 轮：** 只调整新版本条目的校正幅度，并做首层不校正对照；未改善。
- **第 16 轮：** 改用近期历史物品作为校准 query；未超过较好点。
- **第 17 轮：** 拟合中心化教师分数误差；未超过较好点。

**重要收获：** 新版本物品信息有效；增加容量、覆盖或训练轮数并不自动改善推荐质量。

## 阶段四：质量突破与存储纠偏（第 18–20 轮）

- **第 18 轮：** 冻结有效的 Item 映射，再拟合 query 响应残差，恢复约 **83.65%**；但需保存完整额外 K/V。
- **第 19 轮：** 将额外 K/V 改为紧凑隐向量，利用因式分解读取，避免完整缓存复制；同时缩短训练做对照。
- **第 20 轮：** 用可微紧凑读取从零校准，得到 **84.98% 恢复／10.46% 计算／16.67% 额外状态**。

这个结果通过了当时单边万人开发协议。后来确认它使用逐请求 Fresh 参照，不能证明当前一次重建目标达标。

## 阶段五：连续版本与 Design 2 的重新定位

把验证扩展到 V2→V3→V4→V5，保持真实缓存跨版本延续。
最初检查“跨版本误差累积”，却发现逐层读取校正已经缓解部分问题，原 Design 2 动机不足。

随后完成十项缺口诊断，重点检查校准误差与推荐质量、组件相互作用、层贡献、真实写入和用户分布。
发现：**更接近教师不必然带来更高 AUC，组件效果也随发布变化。**

- **协调第 1 轮：** 小样本拟合固定或 query 条件化的 K/V/Response 强度；验证均选回原始配置。
- **协调第 2 轮：** 扩大拟合用户；部分边改善、部分边下降，动态方式没有明确优势。
- **协调第 3 轮：** 增加组件交互特征；仍选回原始配置。另做固定组件选择与独立用户迁移检查。

**重要纠偏：** Design 2 转向发布前离线校准；服务时不知道请求真实反馈，不能描述成在线发现质量低再修复。
另一个 512 用户面板的迁移检查出现负结果，单一开发面板上的收益没有确立迁移效果。

## 阶段六：组织三个模块，并纠正系统成本

集成读取校正、离线准备与状态生命周期，实现发布绑定、追加/淘汰、显式重建及因果依赖清除。
反复调整论文叙事和统一结构图，明确三个模块各自的职责，而非要求每个模块单独贡献明显 AUC。

成本检查暴露了两件关键问题：

1. **质量样本、校准人数、服务人口不能混为一谈。** 早期约 40% 的费用来自不同人口和发布范围，不能与旧单边 10.46% 直接比较。
2. **Full 必须是每用户每次发布重建一次，随后增量服务。** 逐请求 Fresh 不能作系统成本的 100% 参照。

在固定 30k 真实服务轨迹上重新核算后，旧 task 方案为 **75.58% 恢复／94.99% 完整成本**，
最终打分蒸馏也没有解决问题。旧路径的 query 新增计算约为原生 query 的 229%，
说明需要重做读取结构，不能只靠人口摊销或换分母让费用变小。

## 阶段七：按正确边界重做轻量读取

固定连续 4096 用户质量面板和独立 30k 服务成本账，围绕“一份原生 K/V＋窄 code＋一次 attention”迭代。

| 本轮尝试 | 大概做了什么、留下什么 |
| --- | --- |
| Value rank4 | 先实现窄编码与融合读取，恢复约 58.13% |
| Value rank8 | 扩大编码，恢复约 64.89% |
| Query＋Value | 加入 query 对分数的校正；未改善 |
| Query＋Value＋任务强度 | 再用历史反馈校准强度；未改善 |
| Decoder 校准 | 固定编码，仅用最终教师分数优化解码；未改善 |
| 完整 item 输入 | 每个 head 读取完整物品 embedding，避免原始向量切片的限制；单独改动未改善 |
| 按需编码 | 发布只绑定参数，首读才编码，之后增量维护；减少未使用的准备工作 |
| 更长局部训练 | 保留按需编码，延长读取拟合；未改善 |

在同缓存、同优化条件下比较原生与校正 query。计算比例与真实查询耗时分别记录。

## 这一路最重要的几件事

1. **从复现 H 转向解决目标。** Q/H 证明方向有潜力，方法结构允许根据证据调整。
2. **Current 物品信息与联合拟合成为有效组成。** 紧凑 code 同时避免完整 K/V 副本和重复历史扫描。
3. **误差变小不等于推荐变好。** 这一点在早期诊断和后来的 Key 直接监督中都出现。
4. **成本边界必须先正确。** 一次重建、完整服务轨迹、固定共享校准及原生 query 开销分别算清。
5. **单边成功不能代替连续部署与迁移。** 当前结果是开发证据；成本已落入预算，恢复目标与更广验证仍未完成。
