## 当前目标与分工

Full 指每次发布、每个用户在首次请求时重建一次 KV，之后正常增量写入和查询。
完整方法的目标是稳定地恢复较高比例的 Rebuild−Reuse AUC 缺口；80%保留为历史量化参考，
单一开发样本跨线不构成设计成功。每块需有明确机制理由和匹配验证，整体还需独立迁移与服务证据。
新增计算不超过一次重建增量的 20%，并保持少量额外用户状态。
10%–20% 是期望成本范围，低于 10% 同样满足计算要求。
新增 query 工作还要直接与原生 query 比较，不能只用历史重建的大分母掩盖开销。

| 部分 | 问题与当前机制 |
| --- | --- |
| 论文第1节：离线校准（实验D2） | 少量用户提供 Current 重建教师；逐层读取初始化后，通过完整 query 路径联合拟合编码器和投影，独立用户验证，发布后参数固定 |
| 论文第2节：在线读取（实验D1） | 将旧 KV 和 Current 物品信息编码为窄 code；同一次 attention 修正Key分数、聚合Value与code，投影后修正read，保留原生写入 |
| 论文第3节：持续状态（实验D3） | 发布绑定目标，首次读取时初始化 code，原生追加/淘汰与 code 对齐；继承flag限定逐行残差，重建或全层依赖清除后退出校正 |

三个模块分别定义如何读、如何准备参数、如何维护状态，共同承担整体目标。
不要求各自产生巨大独立 AUC 提升。当前 D2 使用发布前可构造的教师分数，
服务时不访问重建教师或当前请求的未知反馈。
D3 的依赖标记描述旧状态的因果来源，不预测推荐质量；清除也不表示与每次请求重建相等。
收益驱动的重建调度、并发发布和负载服务仍未验证。

## 已完成到哪里

新路径已完成真实连续 `V2→V3→V4→V5` 回放、融合算子与生命周期验证。
当前选定完整开发点是 `fullitem8_local_kv32_joint16_support_lazy`：
**84.807% 恢复 / 18.438% 完整计算 / 12.5% code 状态**，使用继承flag限制row残差；
原未门控版本76.136%／18.430%保留为匹配控制。新点不是独立确认，也不以跨过80%宣布最终成功。
Response16、增加早期验证点和完整原生状态输入均未改善，全部负结果保留。
once-Rebuild Key 的读取干预已完成：在 joint16 上的恢复点估计为84.496%，
配对增益区间仍跨0。这种教师干预不能进入可执行方法前沿。
只在最终联合校准中加入可学习Key得到71.020%/16.878%，未改善。
把Key学习提前到逐层读取拟合已完成上述76.136%的结果。
再加入固定1倍逐条Key差值监督的完整结果为65.624%／19.286%，没有改善，不采纳。
最新Value容量对照rank12为64.605%／18.895%，matched rank8为69.312%／13.960%，均未超过选定点。
全部对照保留在设计计划；论文已按当前冻结开发候选更新，仍明确开发选择、区间及适用范围，不是最终独立确认。

质量使用固定 4096 用户、51,731 请求的开发面板；完整费用使用另行固定的
30,000 用户、393,521 请求真实服务轨迹。费用是逐事件形状的 FLOPs 核算，
不是 30,000 用户 GPU 质量或服务延迟测量。
每版分别计算 AUC，恢复率为各版等权平均 AUC 增益除以 Rebuild 的平均增益，
不平均各版恢复率，也不混合跨版请求后算一次 AUC。

共享校准、质量样本和部署人口是三个独立规模。
主设置把已有 native KV 作为系统输入，计入教师构造、拟合、验证和全部服务新增工作；
需要额外重建校准源状态时，另报该完整成本情形。
当前使用固定 256 fit / 16 validation 用户；这些人数不是未来部署人口上限。
开发面板已参与多轮选择，不能称作新用户盲测；后续确认须先冻结方法与角色。
