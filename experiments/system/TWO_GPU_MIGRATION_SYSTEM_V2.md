# KuaiRand two-GPU cohort migration system v2

## Status

`kuairand_long_context_4plus12_two_gpu_migration_system_v2` is the first
real-checkpoint result that closes the algorithm, operator, and host-backed two-GPU runtime path
under one system boundary. It supersedes the performance interpretation of the synchronous exact
baseline in `KUAIRAND_PROGRESSIVE_SYNC_V1.md`; it does not supersede that file's historical
diagnostics.

The run is still `adaptive_seed0_system_development`, not confirmatory paper evidence. The
compiled programs were developed on training seed 0, and the controlled version mix is assigned
rather than generated by a complete update job. Recommendation quality comes only from the
existing verified-compiler protocol. This system benchmark reads no recommendation labels and
does not change the published programs.

## System definition

The implemented path has three connected layers:

1. The verified cohort compiler supplies one attention-weighted full-affine program for each
   theta0/theta4/theta10-to-theta11 version pair. Every stale extent receives the compiled repair;
   version is a compilation and batching key, not a reuse-safety oracle.
2. A Triton capsule-to-K/V operator fuses affine projection, bias, length masking, and K/V split,
   then writes separate contiguous K and V tensors directly.
3. A host-backed cohort engine keeps all three programs resident per GPU, dispatches mixed source
   cohorts, overlaps pinned-host H2D, compute, and D2H on three streams, publishes into persistent
   pinned extents, and assigns batches across two GPUs using longest-processing-time-first
   scheduling.

The exact baseline has the same asynchronous raw-host-to-FP16-K/V-host boundary. It replicates the
current model on each GPU, uses the same three-stage pipeline and persistent output extents, and is
independently tuned without source-version grouping. Both BF16 and FP32 model execution are
reported. This avoids comparing the migration engine against the earlier synchronous baseline.

## Protocol

- Command:
  `CUDA_VISIBLE_DEVICES=0,1 python scripts/benchmark_kuairand_two_gpu_migration_system.py`
- Local result:
  `results/system/kuairand_long_context_4plus12_two_gpu_migration_system_seed0.json`
- Hardware: two NVIDIA A40 GPUs; the physical pair is GPU 0/1 on one NUMA node with NV4 peer access
- Model: 16 layers, hidden/K/V width 512, maximum full sequence 2,048
- Target: theta11 on D16
- Source mix: 13 theta0, 19 theta4, and 32 theta10 records
- Trace: 64 real histories sampled from the verified compiler's 522 final-test users
- Logical prefix tokens: 98,252
- Timing: one warmup and three complete measured repetitions; tables report medians
- Migration layout: batch 1, 32-token buckets, three in-flight batches, source-version grouping
- Exact layout: batch 2, 32-token buckets, three in-flight batches, no source-version grouping
- Publication: complete FP16 K/V in persistent pinned host memory
- Included: pinned H2D, operator/model execution, pinned D2H, worker and scheduling overhead
- Excluded: checkpoint loading, old-capsule materialization, program fitting/compilation, serving
  interference, and storage below host DRAM

The first 32 users under the deterministic system ordering were used only for label-free layout
search. The next 64 users form the disjoint final systems trace. The search retained batch/bucket/
inflight settings only when they improved throughput or padding. On the search trace, removing
length bucketing reduced migration throughput from 863.2 to 643.1 records/s; the selected
32-token bucket was also faster than adjacent 16- and 64-token buckets. Exact recomputation was
tuned separately and selected batch 2 rather than migration's batch 1.

## Algorithm provenance

The runtime loads only actions already published by
`kuairand_long_context_4plus12_verified_compiler_v1`.

| Source | Certificate cost/exact | Worst recovery lower bound | Worst coverage lower bound |
|---|---:|---:|---:|
| theta0 | 0.0627 | 0.8530 | 0.9224 |
| theta4 | 0.0631 | 0.8373 | 0.9005 |
| theta10 | 0.0631 | 0.9228 | 0.9459 |

On the separate 522-user recommendation evaluation, these programs recover
88.6%/89.1%/93.6% of the K/V gap at ages 11/7/1. Those quality values are not re-estimated from
the 64 systems users and are not independent training-seed replications.

## Operator result

The representative resident batch has one record and sequence width 2,047.

| Operator | Median | Relative K/V error from FP32 | K/V contiguous |
|---|---:|---:|---:|
| FP32 reference | 3.119 ms | 0 | no |
| packed FP16 `baddbmm` | 0.838 ms | 3.66e-4 | no |
| fused FP16 Triton | 0.706 ms | 3.66e-4 | yes |

Packed FP16 is 3.72x faster than the FP32 implementation. Fusing the epilogue and writing
contiguous K/V is another 1.19x over packed FP16. Across the complete one-GPU host-backed path,
the same change improves time from 162.5 ms to 138.1 ms, or 1.176x. The operator therefore changes
both resident kernel time and end-to-end publication time rather than being a synthetic-only win.

The strongest exact baseline uses BF16 model execution and FP16 publication. On a resident
batch-two, length-2,047 input it takes 71.23 ms versus 101.12 ms for FP32. Its published K/V has
3.53e-3 relative error from FP32 and contains no NaN or Inf. FP32 exact remains reported as the
semantic numerical reference.

## End-to-end result

| Configuration | Completion time | Throughput | Assigned-work imbalance |
|---|---:|---:|---:|
| packed, dynamic output, 1 GPU | 162.5 ms | 393.8 records/s | 0 |
| fused, dynamic output, 1 GPU | 138.1 ms | 463.3 records/s | 0 |
| fused, persistent output, 1 GPU | 138.2 ms | 463.2 records/s | 0 |
| fused, persistent, round robin, 2 GPU | 71.60 ms | 893.9 records/s | 0.36% |
| fused, persistent, LPT, 2 GPU | 70.82 ms | 903.7 records/s | 0.03% |
| full recompute BF16, 1 GPU | 1.564 s | 40.9 records/s | 0 |
| full recompute BF16, 2 GPU | 794.3 ms | 80.6 records/s | 0.02% |
| full recompute FP32, 1 GPU | 2.224 s | 28.8 records/s | 0 |
| full recompute FP32, 2 GPU | 1.116 s | 57.3 records/s | 0.02% |

The selected migration path scales 1.951x from one to two GPUs, or 97.5% parallel efficiency.
LPT contributes only 1.011x over round robin on this fine-grained trace; its value is the explicit
load bound and robustness to less balanced extent sets, not a large standalone speedup here.
Against the independently tuned two-GPU BF16 full-recompute engine, migration is 11.22x faster
end to end. The resident-kernel advantage therefore survives real capsule reads and complete K/V
publication on this controlled host-backed workload.

Persistent output allocation is deliberately retained despite a 0.9998x steady-state throughput
ratio. It fixes destination addresses and removes first-registration variance; it is not claimed
as a steady-state speed optimization.

## Capacity and placement

| State | Size |
|---|---:|
| Padded old `Norm(x)` capsules | 1.507 GiB |
| Logical old FP16 K/V | 2.998 GiB |
| Persistent target FP16 K/V | 3.014 GiB |
| Raw exact histories | 1.88 MiB |
| Three FP16 program replicas across two GPUs | 96.2 MiB |
| Two FP32 current-model replicas | 1.349 GiB |

The unpadded normalized capsule is exactly 50% of logical FP16 K/V capacity. This round accepts
that space-for-time cost. The model and three small program tables are replicated; cache extents
are partitioned, so this two-GPU design requires no peer cache transfer. Host NUMA placement is
not an experimental variable because the chosen physical GPU pair shares NUMA node 0.

## Decision and current successor

This result is sufficient to retain the three-layer system design:

- verified version-cohort compilation supplies the computation;
- the fused direct-write operator supplies a real operator-level gain;
- length organization, streaming movement, and two-GPU extent scheduling preserve the gain at the
  complete host boundary.

It does not yet establish an OSDI/EuroSys-complete evaluation. The current successor is the
destination-oriented out-of-core update job defined in
`experiments/system/DESTINATION_OUT_OF_CORE_V4.md`. Its next gates are:

1. replace the 64-record controlled trace with the complete fixed update cohort;
2. bound HBM and host staging with waves and publication backpressure;
3. compare compiled and full-recompute paths at identical HBM and DRAM destinations;
4. report calibration amortization, complete-job bytes, peak memory, manifest commit, and
   1/2/4-GPU completion time;
5. treat filesystem/remote adapters as correctness interfaces until real SSD or network hardware
   receives a separate protocol.
