## 固定的任务和成功标准

给定用户过去的曝光行为，用带候选查询的因果 HSTU 为**当前请求的完整排序阶段候选集**评分。
主指标为逐请求计算再平均的 observed-positive **NDCG@10**，辅指标 Recall@10，
@5/@20 为预声明敏感性分析。候选不随机替换、不根据方法分数截断，也不按正例位置补候选。
零正例请求不进入 NDCG 均值，单列数量和比例；原始分数、候选数和分母全部保留。

正例为真实曝光且 `effective_view=1`。未曝光是反馈未知，指标中的零观测增益不代表真实不喜欢。
因此这能支持“在日志候选中排前已观察到的有效观看”，不能当作无偏线上效用。
标签和候选来源比指标名称更关键，不声称任何单一指标能排除全部质疑。

要观察的失配是同一新模型、同一历史、同一候选下：

`Δ = NDCG@10(current model, current KV) − NDCG@10(current model, parent KV)`。

至少一个真实更新边的 Δ 为正且用户聚类配对区间支持下降，才支持本轮的缓存失配动机。
保留 `parent model + parent KV` 作为背景参照；**不要求新版原生质量超过旧版原生质量**。
不调大学习率制造退化，不损坏缓存，不按测试表现选择用户或发布边。
首次确认预先指定 M0→M1；其余八条全部报告，不能事后选最大下降再称为预先指定的检验。
确认 UID 在配方冻结前不查看。D28–36 对应九条发布边，D37 仅额外检验最新 M8→M9，
不拿 D37 一天冒充九条边各自的发布窗口。
正负结果都保留；小模型没有差距时先诊断历史依赖、训练和实现，最多检查前两条开发边，
不自动跑完整链来碰运气。

## 推荐时间线：15 天基模训练、9 次每日更新

[RecFlow 论文 §2.1](https://arxiv.org/html/2410.20868v1#S2.SS1)说明：D1–23 仅保留部分阶段样本，
D24–37 才保存完整后段候选。因此完整候选协议下不能为早期版本伪造完整评测池。
相比机械使用 D1–15 + 九次两日更新，更推荐下面的安排。
原始 37 天曝光时间范围已核查：文件日期采用北京时间，request_timestamp 为 Unix 毫秒。
所有窗口显式使用 `Asia/Shanghai` 的 `[当天 00:00, 次日 00:00)`，不依赖执行主机时区。

| 阶段 | 日期 / 天数 | 用途 |
| --- | --- | --- |
| 历史积累 | 01-13 至 01-23，D1–11 | 作为后续训练请求的历史，不产生训练目标 |
| 基模预训练 | 01-24 至 02-04，D12–23 | 真实曝光反馈 BCE，学长历史和物品特征 |
| 基模候选对齐 | 02-05 至 02-07，D24–26 | 完整候选上的排序训练，产出 M0 |
| 连续更新 | 02-08 至 02-16，D27–35 | 每天增量训练一次，M1…M9，不重置参数和优化器 |
| 各版评测 | M0 用 D27；M1…M9 各用 D28…D36 | 每版只评训练截止后的完整一天 |
| 最终时间窗口检查 | 02-18，D37 | 冻结配方后，在确认用户上额外检查最新发布边 |

以上是时间切分的离线发布模拟，不宣称训练结束没有延迟、可以在次日零点实时上线。
部署延迟若成为论文问题，需要另行定义真实可服务时间。
D27 等日期可以是 M0 的评测日和 M1 的训练日，但 UID 角色严格分离。
后续版本从不使用确认用户的标签做梯度或选模型。完整日程见 [reports/schedule.json](reports/schedule.json)。

## 模型、长历史与训练目标

采用 **HSTU-reference 的 SiLU 注意力、相对位置偏置和候选独立查询**。
这是本仓库的研究实现，不冒称复现工业 HSTU 的完整特征/内核。
历史侧编码一次；候选的 item/author/category 等信息形成查询，各自在每层读取历史 KV，
通过共享标量头输出分数。候选互相不可见，查询不写入持久历史。
这样既是明确的排序任务，也保留论文需要的历史 KV、候选条件读取和版本失配。

| 配置 | 层 / 宽 / 头 | 历史 | 用途 |
| --- | --- | --- | --- |
| 小模型 | 2 / 128 / 4×32 | 最大 1024 | 先验证数据、学习、真实更新及失配 |
| 主配置候选 | 8 / 256 / 8×32 | 最大 1024 | 吞吐和小模型通过后再训练 |
| 预算收缩候选 | 6 / 256 / 8×32 | 最大 1024 | 8 层超时才考虑，保留真实长历史 |
| 后续大配置 | 12 / 384 / 12×32 | 最大 1024 | 第一条有效链完成后再决定，不自动启动 |

小模型缩宽度、层数和训练人口，保留完整候选和最近 1024 条历史；所有规模和版本采用同一历史上限。
内部序列容量为 1025，包含 1024 条历史和一个瞬时候选查询；查询不占持久 KV 的历史行数。
正式居民按 D26 截止前至少 1024 条历史确定。现有曝光索引可行性计数为 7375 人，
新流程去重后需重新核实。预检查统计原始累计历史长度，模型按最近 1024 条截取。
人口不按以后每天活跃的交集筛选；每日报告实际活跃人数，不把无请求用户当质量零。
随机 UID 哈希划分 train/validation/development/confirmation 为 70/10/10/10。
该哈希下 D26 已满 1024 历史的可行性计数分别为 5197 / 734 / 694 / 750；尚非去重后的最终人口。
foundation 的训练目标允许短历史请求，正式长历史居民的质量单独汇报；不能只靠 padding 宣称长序列。

初版物品表示建议 **64 维 ID 表再投影**到模型宽度，并叠加作者、两级类别、时长等已有特征。
显式表先取 foundation 训练数据频次前 1,048,576 个 ID，其余 262,144 个固定哈希桶；
所有版本共享映射，未知物品仍参加排序。实际覆盖、碰撞和新物品质量必须报告，
必要时只在开发阶段扩大表。这样避免用几十百万完整宽度 ID 把预算主要花在优化器和通信上。
不把现有 Large/Max 的总参数量作为新任务的强制目标。

初版排序损失：逐请求归一化的曝光 BCE + `λ × 完整候选多正例交叉熵`。
BCE 只吃真实曝光反馈；listwise 部分将未曝光候选作为弱监督竞争项，存在曝光偏差。
只比较 λ=0 和 0.1 两种简单开发配置，使用 D24–26 的预发布 validation UID 原生 NDCG 和损失选定，
先选定 foundation 配方，再进行 M1/M2 开发用户检查；
不按哪个配置产生更大缓存下降来选。分块只改变执行，softmax 分母跨完整候选集。
候选标签 `-1/0/1` 分别保留未知/已曝光无效/已曝光有效三种状态。
训练 BF16，正式原生质量和缓存失配均用 FP32 参数计算、FP32 KV 和同一读取实现。
初版 input dropout 与 attention dropout 都显式设为 0，避免依赖模型类的隐含默认值。

## 数据工程和时间因果

新建 daily candidates CSR（request offsets + raw item IDs/features/labels），
历史按用户共用一份事件数组，每条请求只存 history start/stop。
不展开“请求 × 候选 × 历史”的重复文件，不在训练循环中调用 Pandas groupby。
按天并行扫描 Arrow，投影必要列，暂定 4 个日文件 worker × 每个 4 个 Arrow 线程，
分片后 mmap、长度分桶、pinned-memory 预取。根据实测 I/O 再调并发。

候选阶段成员需先确认实际 `rank_index` 的缺省值与含义，不能只用 `rank_pos | rank_neg` 代替完整池。
真实反馈以 `realshow` 原始日志为依据，与 `all_stage` 的同键字段做一致性核对。
每个请求按 `(user_id, request_id, video_id)` 去重；冲突字段、缺失曝光/正例关联必须报告并阻止训练，
不能默默补正例。候选数按实际数据分布处理，不硬编码 430/500。
排序位置、阶段标签、当前曝光和当前反馈只用于离线构建集合/监督，绝不进入查询特征。

历史仅写真实曝光；同一用户同一 request_timestamp 的所有请求都排除在当前前缀外。
同时间事件采用固定顺序，并不声称这是用户真实观看次序。
这里采用常见的 request-time 日志回放假设：先前请求反馈可用于后续历史。
数据没有完整反馈到达时钟，不能声称已证明严格在线反馈延迟因果；未来若讨论延迟需另设协议。
已有 processed arrays 只用于可行性审计，不继承旧角色、旧词表和候选池。

## 评测窗口和缓存比较

小模型先完成 M0→M1，再看 M1→M2；每次更新的下一整天既用于 native 请求排序质量，
也提供缓存比较的请求。选每名预定居民当天第一条请求，以该请求之前的同一历史，
分别用父版/新版构造 KV，再由同一个新版读它们，隔离“权重版本不匹配”。
零正例请求仍保留记录；质量均值仅用正例请求。用户聚类 bootstrap 保持 request-macro 口径。
第一条从 `all_stage` 的完整请求索引选，包括无曝光请求，不改选“第一条有正反馈的请求”。

这是**相邻版本的固定历史兼容性实验**，不是一天持续在线缓存轨迹。
它足以回答本轮“真实训练更新后是否存在复用损失”的第一问题。
通过后再接真实发布时的缓存、逐请求追加和淘汰，以完整日窗口评估持续复用；
这部分必须单独记录状态语义，不能把快照实验写成 serving 实验。
新增单模型 cache identity、候选独立性和完整重建数值检查先于任何质量宣称。

## 预算和推进顺序

1. 数据到齐：核查 schema、成员、关联、长历史、词表和角色；冻结清单和哈希。
2. 小模型：固定最多 1024 个训练 UID，开发/验证 UID 单独取，最多两条更新边；
   两个 λ 配置的总预算上限 3 小时。开发分数需优于随机和训练集流行度，
   同时用 128 历史截断做一次配对诊断，观察对更早历史的依赖。保留负结果。
   该推理截断会改变输入分布，不能单凭它宣称长历史训练优于短历史训练。
3. 吞吐：用真实长度/候选数、真实 embedding 表和完整 forward/backward/optimizer，
   每个候选硬件组合测约 200 步，再测验证和 checkpoint。先预热再计时。
   BF16 计算、FP32 参数，比较 1/2/4 卡；不把合成数据或旧曝光训练耗时当预算证明。
4. 主基模：预计含编译、验证、保存的耗时加 25% 余量后需 ≤12 小时才准入，
   **运行硬上限 15 小时**。下载/一次 CPU 预处理另计并报告。
   更新目标 ≤1 小时/版，硬限 2 小时/版。估计超限先改执行、训练请求预算或层宽，
   不在训练中突然缩短主历史或删掉测试候选。
5. 真实小链通过后才启动 M0…M9。到时限先保存可恢复状态并记为 budget_limited，
   不把未完成训练冒充完整基模，也不无休止续跑。

本次 g202 检查为 4×A40 46 GB、112 逻辑 CPU；NVLink 连的是 0–1 和 2–3 两对，
跨两对经过系统互连。四卡不必然最快，先测两卡 vs 四卡的通信占比。
从标准 DDP 开始，梯度累积减少同步；若 ID 梯度通信成为瓶颈，再考虑已验证的紧凑行通信，
不能直接用陈旧稀疏优化器近似改变 AdamW 语义。每次开跑重新确认卡的占用。
不在各候选上复制 KV；查询分块/激活重算减少内存，但不改变全候选损失。
不得缓存跨 optimizer step 的训练前缀，否则梯度对应旧参数。
各卡按全局有效请求数归一化，包括完整梯度累积窗口；全局空步骤不执行 optimizer/weight decay。
比较卡数时保持全局有效 batch 64 个请求，调整每卡 microbatch 和累积次数。
DataLoader 用 spawn，每训练进程先限 2 个 CPU 计算线程，避免 NCCL fork 死锁和线程过度嵌套。
新版加载父版 optimizer 后显式重设 update LR 与当日 scheduler，避免继承已衰减到零的学习率。
checkpoint 同时保存匹配的模型、优化器、scheduler、RNG、样本游标和输入哈希。

## 当前已落地和未完成的部分

- `code/protocol.py`：日程、14 文件清单、未知反馈分离、标准请求 NDCG/Recall、配对 UID 区间。
- `code/preflight.py`：CPU 数据覆盖/长历史/硬件检查；缺阶段文件明确阻止训练准备度。
- `code/ingest_archive.py`：支持 tar/zip，仅落盘需要的 14 天，逐文件 SHA、空间检查和同内容续接。
- `code/configuration.py`：校验 1024 历史、日程、角色隔离；统一生成各规模 backbone 配置。
- `code/objective.py`：曝光 BCE 与完整候选 listwise 目标的可验证参考实现。
- `code/shared_reader.py`：HSTU-reference 共享历史读取原型；支持相对位置和真实长度。
  用原生逐候选 append 校验分数/梯度，避免复制整份 KV 到每个候选；支持查询激活重算和外部物品特征。
- `code/check_reader_gpu.py`：1024 历史 FP32/BF16 数值检查、257 候选分块与重算梯度检查。
- `code/check_distributed_loss.py`：双卡 NCCL 的不均衡/空 rank 梯度检查，不执行优化器更新。
- **尚未完成**：原始 all_stage 行级审核与最终转换器、特征编码器、DDP 训练器、
  数据实测吞吐、pilot 权重/质量、正式模型链和持续缓存回放。
  eager 原型不代表高效训练已验收，不自动排队正式模型训练。
