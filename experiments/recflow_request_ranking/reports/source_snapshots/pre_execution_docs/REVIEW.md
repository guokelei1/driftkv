# 数据到齐前的方案复查 — 2026-10-27

结论：1024 历史、完整排序候选、NDCG@10、M0＋九个日更新的方向可以保留；
已发现并修正接入、配置、损失归一化和验证范围的缺口。**尚不能承诺训练后一定出现缓存下降，
也不能用合成数值检查承诺 15 小时内完成真实基模。** 这两件事分别由小模型和真实 batch 测量判断。
本轮没有训练 foundation，没有启动旧队列，没有改论文。
验证结果：23 项 CPU 检查和 lint 通过；A40 上的 1024 历史、FP32/BF16 与
257 候选分块重算数值检查通过；实际双卡 NCCL 的两种有效请求分布检查通过。
这些是执行正确性检查，不是推荐质量或完整训练耗时结果。

## 已修正的问题

| 问题 | 修正 |
| --- | --- |
| 日期文件没有显式绑定时区，按 UTC 切天会错开 8 小时 | 实查全部 37 天曝光边界，按 Asia/Shanghai 的自然日和毫秒构造半开时间区间 |
| 历史从 1024 被自行改成 2048 | 全规模固定最近 1024；内部加一个瞬时查询为 1025；配置加载时拒绝不一致 |
| 文档允许下载压缩包，检查程序却只认解压文件 | 新增 tar/zip 接入，选择 14 天、哈希、空间检查、同内容续接；预检查识别待解压包 |
| schema 未要求模型要用的 duration，损坏文件状态也不明确 | 补 duration；缺列、重复规范化列、坏文件头标为 invalid_headers，始终不能当作训练已就绪 |
| 各卡本地均值直接平均会改变有效请求权重；空卡会抛异常 | 按全局有效请求数归一化，覆盖梯度累积；空卡连通零梯度，全局空步骤跳过优化器 |
| 分块读取但保留所有块的反向图，显存不一定下降 | 支持 non-reentrant 查询激活重算；保留全候选损失分母，并校验分数及梯度 |
| 旧检查只有短序列 CPU，无法证明 1024/BF16 正确 | 增加 A40 上 1024 历史数值对照，以及 257 候选分成 128/128/1 的重算检查 |
| BF16 舍入可能影响微小排序差 | 训练可 BF16；缓存失配和 native 排序质量统一用 FP32 参数计算及 KV，同一读取实现 |
| 学习率、dropout 和恢复状态存在隐含默认值 | dropout 显式为 0；更新恢复 optimizer 后重设 LR/scheduler；checkpoint 要保存匹配状态 |
| 日程/角色/模型配置各自维护，可能再次漂移 | 集中校验日程与角色，所有 backbone 从同一 proposal 构造 |
| 小模型第一请求容易被误实现成“第一条有曝光/有正例” | 从完整 all_stage 请求索引选第一条，零曝光/零正例照常记录，不事后换请求 |
| 模型选择和确认窗口不够明确 | λ 按 D24–26 预发布 validation UID 选择；首个确认边固定 M0→M1；八条次要边全部保留 |
| 推理时截短历史被说成已证明长历史训练的价值 | 仅作为历史依赖诊断；比较训练策略优势需要独立匹配的长/短历史训练 |

单卡和多卡数学约定参考 [PyTorch 2.12 DDP 文档](https://docs.pytorch.org/docs/2.12/generated/torch.nn.parallel.DistributedDataParallel.html)：
DDP 平均各 rank 的梯度，所以各 rank 使用 `local_loss_sum × world_size / global_active_requests`。
global_active_requests 覆盖完整累积窗口；不再额外除以累积次数。
实际双卡 NCCL 已检查不均衡有效请求数及一张卡完全无有效反馈两种情况，梯度均与整体计算一致，
记录见 [reports/distributed_loss_audit.json](reports/distributed_loss_audit.json)。
验证/测试分布式分片不得用 DistributedSampler 补齐后重复计数；按 request key 无重复合并，
所有方法必须提交相同的请求和候选 key 集合。

## 时间和实验语义

从 [RecFlow 收集协议](https://arxiv.org/html/2410.20868v1#S2.SS1)确认，完整后段候选仅覆盖最后 14 天。
因此采用 D1–11 历史、D12–23 预训练、D24–26 候选对齐，随后 D27–35 每日更新。
M0…M9 的评测日依次是 D27…D36。M1…M9 的缓存比较在 D28…D36，正式确认用户在配方
冻结前不查看；D37 是最新 M8→M9 的额外时间窗口，不代替前九条各自的窗口。

现有曝光索引中 D26 ≥1024 历史为 7375 人，按新哈希角色分为 5197/734/694/750。
37 天曝光时间范围见 [reports/exposure_time_audit.json](reports/exposure_time_audit.json)，
全部落在对应北京时间自然日内，且上一日最大时间戳小于下一日最小时间戳。
这些是人口可行性统计，不是预测质量，也未继承旧实验的人口角色。
真实去重后的历史长度、完整阶段请求中的每日活跃覆盖，仍要在新预处理时重算。

第一阶段缓存比较为相同 1024 事件前缀的父版 KV 和新版 KV，由同一个新版评分，
只检验权重版本不匹配。父版原生质量单独保留，不要求新版更好。
快照前缀必须在两端采用同样的构建方式；不能一端用长期增量 FIFO 状态，另一端用最近
1024 条从头重建，再把两种历史语义的差异全部算作版本失配。连续 serving 轨迹另行接入。

真实标签来自曝光日志；未曝光保留未知状态。阶段 rank_index 的有效值规则、候选数和
曝光关联必须看实际 all_stage，不能照着“通常约几百个候选”硬编码。
历史反馈可用时间仍采用 request-time 回放假设；原始数据不提供完整反馈到达时钟。

## 下一次数据到齐后的执行顺序

1. 确认下载完成和文件位置；已有 Feather 直接核验，有压缩包则只解所需 14 天。
   保存每个文件 SHA 和行数、schema、时间覆盖；异常停止在对应输入，不覆盖原文件。
2. 检查 rank_index 缺省值和完整阶段成员，按键去重并与 realshow 核对全部曝光/反馈。
   严格区分请求时间的毫秒与其他字段可能的秒；规范化真实列名的前导空格。
   本机 realshow 实际有 ` category_level_two`，不能假定所有字段完全匹配 README。
3. 在未看模型质量前固定 UID 角色、D26 人口、训练/验证/开发/确认请求清单、词表与特征映射。
   候选 OOV 一律保留。报告显式 ID、哈希、新物品覆盖和碰撞，禁止只留下模型认识的候选。
4. 实现 daily CSR/mmap 转换器、特征编码器和 DDP 训练入口。外部特征编码器替代原 item 表时，
   移除或冻结未使用的占位参数，防止 DDP 等待永远不存在的梯度；检查每个预期训练参数的梯度。
   预处理按天并行，训练路径不临时 Pandas groupby、不复制每个候选的整份历史。
5. 用训练角色中的少量真实请求先跑输入/标签/反向和小批过拟合诊断，再做受控小模型。
   不动确认用户，不用开发/确认标签更新参数。小模型也用 1024 和完整候选。
6. λ=0/0.1 仅在基模开发阶段对照，按预发布验证选择。M0→M1（必要时 M1→M2）先检查学习
   和缓存失配；全部符号保留。没有信号就诊断，不伪造漂移，不自动排九个大训练任务。
7. 用真实特征表、候选/长度分布、forward/backward/optimizer/同步/I/O，比较 1/2/4 卡。
   保持全局 batch 64，给预热、验证、保存单独计时。保守总投影 ≤12 小时才准入主基模，
   15 小时硬限在训练器内实际执行，并在边界前预留保存时间；中断继续累计已用预算，不能重置时钟。
8. 一条有意义的小链通过后冻结正式配方，再完成 1＋9 链。全链各版 checkpoint/来源/状态
   和正负结果保留。最终比较全部正式窗口，另做 D37 的最新边检查。

## 还不能提前验收的三件事

- 完整候选成员与反馈关联：缺实际 all_stage，文件头和论文不能替代逐行核对。
- 主模型的 15 小时预算：必须含真实大 embedding、完整候选、优化器、DDP、验证和保存。
  小表合成 GPU 数值检查不是吞吐预算证明。
- 真实更新会不会造成可辨认的 NDCG 复用下降：不能从张量误差推断，也不能靠选最大下降的模型保证。

当前已实现接入与正确性基础；正式数据转换器、特征编码器、DDP 训练器和持续回放仍未完成。
下一次可以按上述顺序直接继续，不需要用户再决定常规工程细节。
