# Script inventory

This directory contains only the current HSTU-native foundation, data processing,
Full-only release evaluation and D14/E14 motivation entry points. The concrete
workflow is defined in `docs/experimental_design.md` and the observed result
boundary is defined in `docs/motivation_observations.md`; a filename does not
authorize an experiment.

## Active S/M/L construction

The raw-data downloader is plan-only by default:

```bash
python scripts/download_scale_datasets.py
python scripts/download_scale_datasets.py --download --jobs 2
```

The second command downloads only the current core bundle: Yambda-500M
listens/likes/dislikes and RecFlow realshow. RecFlow request/metadata companions
require `--include-recflow-companion`; the 37 all-stage files additionally require
`--include-recflow-all-stage`. Archives are not extracted automatically.

After the core Yambda files pass download verification, the CPU-only scale
population preparation entry point audits the raw tables and materializes only
compact UID/catalog maps (not expanded event copies):

```bash
PYTHONPATH=src python scripts/prepare_yambda500m_scale_populations.py
```

This earlier population-only audit freezes the Medium selector and Large
eligibility boundary. The current uniform matrix is generated by the unified
builder below: Small/Medium are hash prefixes of 10,000/30,000 users and Large
contains every materializable pre-theta0 user.

The population manifests retain complete timestamps. Build the separate,
label-free physical-day and logical-release plan with:

```bash
PYTHONPATH=src python scripts/plan_yambda500m_streaming_windows.py
```

This planner compares the uniform 14d fixed-endpoint recipe with a prospective
2d fixed-endpoint frequency sensitivity. Neither uses a performance admission
window or checkpoint selection. It reports calendar capacity only; theta3 and
later slots remain locked and it exposes no training or label-reading path.

The current unified scale preprocessing entry point builds all three nested
Yambda-500M datasets together:

```bash
PYTHONPATH=src python scripts/build_yambda500m_unified_scales.py
```

It creates one shared seven-day-bucket Parquet store plus Small/Medium/Large user maps,
foundation item maps and dataset manifests. Small is hash-rank 1..10,000,
Medium is 1..30,000, and Large is every lineage-eligible user. Use `--replace`
only to atomically regenerate this exact derived store after a preprocessing
correction. Logical loader windows remain arbitrary half-open timestamps, including
aligned daily windows; the wider physical bucket avoids pathological tiny-file I/O.
The default loader keeps theta3/later feedback locked.

- F-only manifests and Frozen Base fitting;

### Small foundation chain (implementation/canary authorized)

The prospective contract is
`configs/contracts/yambda500m_small_foundation_chain_v1.yaml`. These entry
points currently enforce the contract's no-long-training boundary:

- `build_yambda500m_foundation_manifests.py`: causal request/snapshot manifests,
  timestamp-group atomicity, request-time as-of Base features and separate
  target/history OOV audits;
- `train_yambda500m_foundation_fsdp.py`: four-rank HSTU-native foundation trainer;
- `evaluate_yambda500m_release_candidates_raw.py` and
  `adjudicate_yambda500m_release_candidates.py`: independent Full-only candidate
  quality before any Reuse evaluation.

The current D14/E14 reproduction uses the v3 recipe matrix, then the D14
one-hop evaluator and its sealed adjudicator. It does not run the old fixed-
endpoint or residual/Base queues.

Keep model, data, transition and accounting primitives independent from orchestration.
No Medium/Large long queue is authorized yet.
